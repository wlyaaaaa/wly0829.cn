出事怎么办 总表过时了 新建、搬家、改名、删库之后，AI 顺手完整刷新一次：重新扫描，看板页和给程序查的仓库清单一起重写，每个文件先写临时内容再整份替换，不会写出半个文件；两份要是一份换了一份没换，一致性检查查得出来。总索引自己的目录里，9 月刷新过 10 次。 登记和现场对不上 一致性检查拿现场重新生成一份来比，报出差在哪一项；只报告，不自动改，也不提交。 GitHub 连不上、命令读不出来 只读的查看照做，要写 GitHub 的动作先停；读失败只算“不知道”，不算“对不上”（为什么，见亮点）。拉取时网络中途断开，只自动重试一次；登录、证书这类错误不重试。 删库前保全没过 停下说清原因；不改成请我验证了事，也不丢只有一份的东西。 总索引自己丢了 它是换机时最先从 GitHub 拉回的三个基座之一，每天的加密系统镜像里还带着它没推送的改动；仓库清单随时能重新扫描生成。换机怎么做见电脑配置与恢复

为什么这样设计 总表只是导航，不是事实。 登记会过时。动手前再读一次真实的 .git 和 GitHub；不这样，搬过家、改过名的目录会被当成原来那个仓库。 能传、能公开、我同意，三件事分开。 网络和分支没问题，不等于内容适合公开；内容能公开，也不等于我同意发布。三样缺一不可，谁也推不出谁。 进了 GitHub 主线才算交付。 推到临时分支、本地 main 提交了，都不算完；要在 GitHub 上的默认分支里找得到这次的提交。 一样东西只存一处。 冻结名单（约法 L24）和公开分级从生效的规则读，计划任务交给电脑配置与恢复，这里不再抄一份。 上不上网站，单独登记。 哪些项目上网站、叫什么名字，写在单独的一份登记里，不会被总表刷新覆盖；新仓库默认不上，忘了登记，测试会拦下来。 大动作入口不假装是一道安全墙。 删库、改公开的入口一度写到 2,746 行，还配了提交前拦密钥的检查，看着很严，其实挡不住一个已经登录 GitHub 的程序直接删库，维护却很重。9 月 27 日我定了：入口瘦身，承认靠 AI 守规矩。现在 896 行，只做几件实事：核对目标、删库前保全并先预演给我看、该验证时请我验证、做完读回；重写后还没有用过的记录，所以功能表里标待验收。拦密钥的检查拆了：AI 对密钥本来就警觉，密钥都在密码中心。
亮点 一个仓库，九个工作目录 几个 AI 同时干活，各开各的临时工作目录。9 月 28 日凌晨，电脑配置与恢复一个仓库就开着 9 个。收尾只看当前窗口，别的目录里做完没合的活就会被忘掉，或者被当成垃圾清掉。总索引把每条分支都拿去和 GitHub 上的主线比：内容已进主线的标“残留，可以收”；有独有提交的写明“主线缺 N 个提交”，先并进去；有没提交改动的只提醒核对，不碰别人的东西。那天它就找出一条比主线多 9 个提交的临时分支。 读不出来，不等于对不上 GitHub 偶尔连不上，Git 命令偶尔失败。要是把“读失败”当成“身份对不上”，AI 可能就去改远端地址，或者认定这是别的仓库。9 月 18 日起两种结论分开：读失败只算“不知道”，停写入和推送、不停查看，也不因为一条命令失败就整个停工；真读到了而且和登记不一样，才算冲突。
