用途与结果

最快了解这个项目

为什么需要它

仓库一多，同名目录、旧路径、临时工作树和多个远端很容易串台。只看当前文件夹干不干净，或听一句“已经推了”，可能漏掉把私密材料送进公开仓库、覆盖别人未提交的修改、分支落后、提交根本没进远端默认分支，以及另一个工作树仍握着唯一内容等真实事故。总索引把这些容易混淆的事实拆开核对。

举个实际例子

“这份代码是不是已经发布了？别只看当前目录，确认一下主分支和其他工作树。”它会告诉我提交在哪、是否进入真实远端默认分支、还有谁的未完成修改；网络读不到就保留未知，不把它说成仓库身份冲突。

最后我会得到什么

最后拿到的不是一张好看的项目列表，而是一份能直接行动的证据：正确仓库与远端、当前可见性、默认分支、全部工作树和分支状态、继续/警告/阻断原因、公开发布还缺什么，以及出错后该从哪里补证或恢复。新仓库还会列出落盘位置、创建回读、登记结果与首次默认分支收敛；真正发布后仍要从远端默认分支再次回读才算交付。

正常时

仓库身份、可见性、远端、默认分支、相关工作树和发布候选都已现场核对时，表示没有 Git 入场阻断；是否提交、推送或发布仍由当前任务授权和候选内容审查决定。

发现问题时

发现未提交修改、分支落后或分叉、工作树独有内容、索引漂移或公开风险时，给出警告或阻断及具体处理项，不覆盖并发施工。

入口不可用或证据不足时

GitHub、远端引用或本地仓库证据不可取得时，可以继续不依赖远端的安全只读或本地工作，但身份、同步和发布结论保持 Unknown（证据不足）。

它负责

  • 确认每个项目实际对应哪个本地代码目录、哪个远端仓库、公开还是私有以及默认分支。
  • 按需要检查一个仓库的所有工作目录、未提交修改和本地与远端差异。
  • 把“网络能推送”“这些内容适合公开”“本次已获准发布”分开判断。
  • 维护可公开的仓库索引和本机私有导航，更新失败时保留上一份完整版本。
  • 说明专门分支、历史材料和仍有任务使用的工作目录为什么要留、何时可退出。
  • 删分支或清理工作目录前找出只存于那里的内容，不让唯一修改消失。
  • 新个人仓库放个人项目目录，工作项目放工作目录；不同用途有固定本地位置，不把唯一副本放临时盘。
  • 新个人仓库先建立本地首个提交，只创建空的私有远端，再正常推送并从远端默认分支确认结果。

它不负责

  • 具体项目自己决定功能、测试和怎样部署。
  • 检查结果显示“可以继续”，仍不等于获得修改、推送或公开授权。
  • 电脑计划任务、端口和备份恢复由 PCConfig 核对。
  • 真正可复用的秘密不能发到公开仓库；其他路径、名称与技术事实按具体内容判断，不按文件类型整类遮掉。
  • 普通提交和推送不要求每次重建完整索引。
  • 它不会在后台自行监视、刷新、提交、推送或删除工作目录。

产品思想与设计核心

01

先核实真实仓库身份

目录名、标题和旧缓存都不能证明远端是谁；动手前先对上远端、默认分支与 Git 共享目录。

02

看全工作树和分支，别只盯当前窗口

未提交修改、独有提交和仍被别的任务使用的工作树都要保留，不能拿当前目录干净替它们作证。

03

网络传输、公开内容与授权三层分开

网络能推不等于内容适合公开，内容适合公开也不等于当前任务已经拿到授权。

04

远端默认分支回读才算真正交付

功能分支对自己的上游显示为零远远不够；目标提交必须能从远端真实默认分支到达，并再次回读。

05

是否公开要看具体内容

仓库名、路径、版本和故障说明不因看着“私有”就自动消失；真正的个人敏感值逐项判断，可复用的密码和令牌始终不能公开。

06

证据不全时只拦高影响动作

仓库身份、可见性或远端不清时停止发布、删除和迁移，但安全的本地工作与只读诊断仍可继续。

07

仓库真变了才更新总账

仓库身份、公开性或长期保留关系变化时，先生成并核对一整份新索引再采用；只查状态不会顺手改登记，也没有后台自动删仓库。

08

清理前先证明没有唯一内容

分支或工作树只有在内容已整合并证明确实冗余，或已有明确保留用途和退出条件时，才进入退役。

完整执行流程

  1. 1
    从普通请求确定真实目标

    先回答这是现有仓库还是新仓库、个人项目还是工作项目、期望的远端可见性和默认分支；目录名字相似时不靠猜。

  2. 2
    先建立正确的本地起点

    新个人仓库放 V:\Personal\Projects\<name>，新工作仓库放 V:\Work\<name>；在真实目录建好预期 main 与首个提交，保持规范工作树干净，不为空目录预登记，也不把仓库或唯一副本放进 Z 盘。

  3. 3
    只创建精确的空 PRIVATE（私有） 远端

    先确认本人账号下同名仓库确实不存在，再把精确本地分支和提交绑定到受保护创建动作；它只创建 private（私有）=true、auto_init=false 的空远端，不顺手带模板或任意参数。

  4. 4
    完成第一次默认分支收敛

    创建回读成功后才配置 origin 并正常推送本地 main；随后现场确认仓库、可见性、真实默认分支、上游关系与目标提交可达性。默认分支不同就明确处理，不能靠猜。

  5. 5
    仓库真实存在后才进总账

    远端与本地身份、首次默认分支收敛都确认后，正常完整刷新才发布公开代际、更新本机导航并推进已有有效基线。最终现场和基线应无差异；只有首次建账或基线损坏才走显式恢复，不重复迁移。

  6. 6
    现有项目先读规则和 Git 状态

    先取得项目自己的业务语义与测试方式，再查看当前状态、远端和分支，保护已有未提交修改，不把别人的施工混进候选。

  7. 7
    有不确定性才做 Admission（入场检查）

    只查 GitHub 可见性时，LiveMetadata 会联网读取现场元数据，但不会执行 git fetch；需要真实领先/落后才用 RefreshRefs 刷新远端引用，发布前再用 ForPublication。普通明确小改不机械打卡。

  8. 8
    检查全部工作树和分支

    比较未提交修改、上游、领先/落后、默认分支可达性、独有提交、专门责任源和必要保留，不只看当前窗口。

  9. 9
    把传输、内容与授权分开

    先判断网络与 Git 目标能否传输，再看候选内容是否适合当前可见性，最后确认本轮授权；三者不能互相推出。

  10. 10
    精确执行，再从远端回读

    只修改和暂存点名文件；本地测试、提交、推送、默认分支可达、部署与用户结果分别验证。临时分支、本地 main 或一条命令成功都不能冒充远端交付。

本页用到的名词

需要核对专业含义时，可以在这里查看它在 GitHub 总索引 项目中的具体用法。

Repository（仓库）
一组 Git 历史、分支和工作文件；本地目录名不能单独证明它对应哪个远端仓库。
Remote（远端）
本地仓库配置的网络目标；总索引会把 remote.origin.url 规范化后与预期 GitHub 身份比较。
Visibility（可见性）
GitHub 仓库的 PUBLIC（公开）、PRIVATE（私有）或 INTERNAL（组织内部）状态；不在闭集内就失败关闭。
Default branch（默认分支）
GitHub 认定的主要整合分支，通常是 main；完成证据必须回到真实远端默认分支。
Worktree（工作树）
同一 Git common directory（共享仓库元数据）连接的一个可编辑目录；一个仓库可以同时有多个工作树。
Upstream（上游跟踪分支）
当前本地分支用来计算领先和落后的远端分支。没有 upstream 时不能直接判断可推送。
Ahead / Behind（领先 / 落后）
本地 HEAD 相对 upstream 独有和缺少的提交数；0/0 不包含未提交文件。
Dirty worktree（脏工作树）
存在 staged（已暂存）、unstaged（未暂存）、untracked（未跟踪）或 conflicted（冲突）文件的工作树。
Admission（入场检查）
在仓库身份、可见性、工作树或同步事实会改变决定时，按需取得结构化证据；不是每次 Git 操作的审批仪式。
Provider（结构化事实提供器）
按固定 schema（字段合同）读取现场 Owner 事实的入口；输出证据，不自动产生授权。
Transport（Git 传输）
fetch、push 等在本地与远端引用之间传输 Git 对象或引用的动作。
Publication（内容发布）
让候选内容进入公开或目标仓库的现实结果；它需要当前可见性、候选内容审查和授权。
Read-back（回读）
动作完成后从真实远端默认分支再次读取提交或内容，防止把本地成功、临时分支或工作树当成交付。
Registry（登记表）
记录仓库身份、精确治理例外或必要保留条件的结构化清单；命中必须按 repo、ref、path、HEAD 等精确条件判断。
Generation（索引代际）
一次完整、不可变的公开索引文档集合；写完并回读后才切换 current 指针。
Projection（兼容投影）
从当前 generation 复制到顶层供人阅读的 Markdown；它可检查 stale（过期），但不是动态决策权威。
Freshness（新鲜度）
证据是 live（现场）、mixed（部分现场）还是 cached（缓存）；字段明确返回，不靠调用者猜。
Fail closed（失败关闭）
身份、可见性、目标或证据不可靠时，只阻断依赖这些事实的写入和传输，同时允许继续只读诊断。
Retention（必要保留）
带 Owner、用途和退出条件的精确工作树保留项；路径或 HEAD 不再匹配时不能继续借它压掉警告。
Retirement candidate（可退役候选）
内容已进入默认分支且没有已知保护的分支或工作树；仍需确认没有活动依赖后才能删除。
Commit-pinned snapshot（固定提交快照）
干净、受限且固定在已知提交的审计工作树；它不同于普通无 upstream 或含独有工作的临时工作树。

系统里实际有什么

下面是当前产品组件，不是概念分类。每一项都对应真实文件、入口或验证链。

01
索引与同步看板

让人快速看到仓库身份、聚合计数和值得复核的同步问题。

由 Git/GitHub 事实生成 Markdown；PUBLIC（公开）/PRIVATE（私有） 名称与路径只有在能改变判断且实际值可公开时才展开，其他内容保留聚合。

02
本机导航登记 v2

把仓库身份定位到已确认的本机 clone，同时保留路径变化和恢复线索。

保存于 ignored（已被版本控制忽略） 的 99_private；读取后仍必须回读目标 .git origin，cache 缺失、过期或冲突时显式失败。公开与否按具体值和当前用途判断。

03
Owner 基线存储 v3

比较完整仓库身份集合与当前 GitHub 现场，发现并收敛新增、删除、可见性或默认分支漂移。

identity与可空local root分存，原子保存current（当前状态）/previous、hash（内容指纹）与回读。普通status零写；正常full refresh在公开generation（代际）和导航更新后自动推进已有有效基线，并保留非阻断过渡历史。

04
Get-GitOwnerStatus

给跨 Owner 消费者一个紧凑、零写的 current（当前状态）/review_needed/blocked/unknown 结论。

先核验总索引自身 .git identity；通过前不读 baseline、registry（登记清单）、GitHub 或任何本地 root。

05
Get-ProjectCognitionSource

分页闭合地提供 GitHub Owner 仓库来源和有界远端提交比较。

固定 v1 schema（数据结构）、repository node id（稳定节点编号）、分页上限、clone origin 回读和最多 64 个比较文件；缺口显式返回。

06
Get-ProjectAdmission

对一个精确仓库给出身份、visibility（公开或私有属性）、worktree（Git 工作树）、branch（分支）、同步和 transport 证据。

v1 schema（数据结构） 区分 metadata（元数据） 与 refs 新鲜度；可用 TargetWorktree/TargetRef 限定顶层决定，同时保留全部 inventory。

07
GitHubIndex.Core

统一 remote（远端仓库） 规范化、NUL status 解析、dirty 汇总、ahead/behind（领先/落后提交数）、默认分支整合和 push guidance。

默认分支完成证据只读取 refs/remotes/origin/<default>，不退回同名本地 branch（分支）。

08
Git artifact governance registry（登记清单）

声明专门 Owner ref、冻结历史和精确必要保留工作树。

schema（数据结构） 固定并在模块加载阶段失败关闭；普通未来 feature branch（分支） 不会因名称相似被隐藏。

09
公开暴露策略与 Hook（钩子）

拦住高置信敏感路径或新加入的凭据形态。

PublicExposurePolicy.psd1 是路径用例单一来源；Hook（钩子） 只用于总索引 bootstrap/repair，是 defense in depth（纵深防护）而非安全证明。

10
原子 refresh 与 generation（代际）

把一次完整快照写成可校验代际，并在中断后保住上一个有效版本。

先写同卷 .incoming、验证闭合集与 hash（内容指纹）、发布兼容投影、回读，再切 current（当前状态）；只留 current（当前状态）+previous。

11
一致性检查器

零业务写入地比较当前 generation（代际）、兼容投影和重新生成结果。

临时输出进入系统 temp；隐藏入口只写 ignored（已被版本控制忽略） 私有 receipt（执行回执），不 stage、commit、push 或授权发布。

12
Owner-local 合同与回归测试

固定 admission（仓库准入检查）、worktree（Git 工作树）、publication、refresh、里程碑和重大动作的边界。

合同只写稳定机制，动态路径和计数现场读取；测试覆盖 schema（数据结构）、失败关闭、原子切换和隐私边界。

8 层证据分别证明什么

Local identity（本地身份）

能证明：当前目录的 origin、Git common directory、HEAD、branch（分支） 和 worktree（Git 工作树） inventory。

不能证明：GitHub 端当前 visibility（公开或私有属性）、默认分支或远端引用。

GitHub metadata（GitHub 元数据）

能证明：现场 repo identity、PUBLIC（公开）/PRIVATE/INTERNAL、默认分支和 URL。

不能证明：本地 refs 已刷新、工作区干净或内容安全。

Remote（远端仓库） refs（远端引用）

能证明：fetch 后 origin/* 与远端引用一致，可计算 ahead/behind（领先/落后提交数） 和默认分支可达。

不能证明：未提交文件已进入 Git，或候选适合公开。

Candidate review（候选审查）

能证明：实际 commits、paths 和新增内容符合当前项目与公开边界。

不能证明：用户已授权外部写入，或 push 已成功。

Transport receipt（传输回执）

能证明：Git push/fetch 命令对明确远端执行成功。

不能证明：远端默认分支已经包含目标 commit，网页或部署已经更新。

Remote（远端仓库） default read-back（远端默认分支回读）

能证明：目标 commit 已从实际 GitHub 默认分支可达。

不能证明：项目构建、Pages 部署或用户可见结果已经验收。

Generation（代际） integrity（代际完整性）

能证明：manifest（清单）、文档闭集、hash（内容指纹）、bytes、projection 和 current（当前状态） pointer 属于同一快照。

不能证明：快照仍是当前动态事实，或它拥有 decision authority。

Owner baseline comparison（Owner 基线比较）

能证明：完整身份集合相对 current（当前状态）/previous 基线是否稳定、待复核或无效。

不能证明：每个仓库的 worktree（Git 工作树）、dirty、branch（分支） 或发布状态。
