文书和材料制作

已有事情经过、必要原件和接收要求时，把它们整理成合同、说明、申请、通知、回复或附件包，同时给出可继续编辑的 Word 和对应 PDF。内容、附件、版面和签名都要核对；电子阅读按需要用彩色层级，打印时再验灰度。文件做好、本人签好、实际送出和对方处理分别记录，不把电脑上的成品当成现实进展。 只改一个 Word 或 PDF 时直接处理该文件，不为一次修改建立完整材料包。

用途与结果

最快了解这个项目

为什么需要它

同一事项往往同时存在原始记录、旧草稿、核对后的成品、签名版、递送版、回执和对方返回版本。只按文件名继续会用错版本；把“文件生成成功”写成现实进展，又会造成漏签、重复递送或错误判断。这个项目把原件、成品、完整性证据和现实步骤拆开，发生中断时仍能从最近一次核对状态继续。

举个实际例子

我可以说：“维修服务没有按约完成，请把购买记录、沟通事实和退款要求整理成可编辑申请、PDF 和附件清单；不确定的地方先列出来。”项目会先核对原件和冲突，再交给我一份可继续修改的文书、一份同内容 PDF 和附件清单。它会说明材料是否需要签名、现在能否递送；没有真实发送和收件证据时，不会说对方已经收到。

最后我会得到什么

我会得到可继续编辑的 DOCX、同一内容版本的 PDF、核对过的附件与自包含材料包，以及当前精确状态、下一步和恢复点。若原件、内容、签名、版面或现实回读不足，我得到的是保留下来的旧版本、具体失败位置、真正未知和一个需要决定的问题，而不是一份看似完整但无法使用的成品。

可以继续制作

本次事项、必要原件和接收要求核对后，用同一内容生成可编辑版、PDF 与附件；正文和页面逐项检查。签名最终是否清楚可见仍看实际页面，不让自动检查越级保证。

需要修正

原件冲突、日期金额不清、附件缺失、签名不符或某页排版失败时保留上次可用版本和具体问题；文件准备好也不等于已经递送。

当前不可用

某份原件、制作或逐页查看工具暂不可用时只暂停相关步骤，保留已核对的内容、旧成品和继续位置，不从旧草稿猜事实。

从哪里开始

直接说明要做合同、说明、申请、通知或材料包，并给必要事实与原件；只改一个 Word/PDF 时直接处理该文件。

需要准备什么

  • 当前事项目标、接收对象和用途
  • 本次已有或新提供的必要原件
  • 本人已知事实及输出、签名或递送要求

文书怎样从原件走到可递送材料 · 8 步

固定当前事项，做成同内容文件，再逐页核对现实进展

文件制作和现实递送分开。项目能核对本地成品是什么、附件是否齐；发送、收到、处理或对方签回，仍要各自有现实证据。

  1. 01先分流这次真的需要正式材料包吗

    只改单个 Word 或 PDF 就直接编辑；只找原件走材料查找，持续工作交付走工作项目。

  2. 02固定事项明确要给谁、为了解决什么

    核对目标、接收对象、期限、已有版本和下一步，不让别的事项或旧草稿混进来。

  3. 03核对原件事实与真正未知分开

    只取必要的购买、沟通等材料；日期、金额或说法冲突时先列出，不靠模板补猜。

  4. 04决定成品先定内容、附件和签名要求

    确认要一份怎样的文书、交付给谁，电子阅读还是打印，以及本人是否需要签名。

  5. 05同源生成一次形成可编辑版与固定版

    Word 与 PDF 使用同一份确认内容，附件按序放入并再次核对；新版本不覆盖旧成品。

  6. 06逐页检查内容、页面和签名各自过关

    重读正文，查看页码、裁切、颜色或打印效果；有签名时看最终页面是否真的清楚可见。

  7. 07交付前冻结形成能带走和重新核对的包

    文书、附件和检查材料齐全才标为可递送；少一件或多混进一件就不放行。

  8. 08现实回读送出、收到和处理分别证明

    “可递送”还没有送出。发送、对方收件、处理与签回各看对应记录；中断从已核对版本继续。

  • 确认真正未定的事实与是否需要签名
  • 决定是否递送、撤回或联系外部对象

项目负责

  • 用同一内容生成 Word、PDF 与附件包
  • 逐页检查文字、排版和签名可见性
  • 保留明确版本、失败位置及下一步

外部结果另核对

文件离开电脑之后
  • 发送记录只证明已经送出
  • 对方或平台确认才证明收到
  • 处理结果与对方签回还需各自证据

它负责

  • 从这次事项与必要原件形成可执行的文书制作方案。
  • 从同一份确认内容生成可编辑 Word、对应 PDF 与附件包。
  • 按实际要求分开无需签名、待本人签名、已签和可递送版本。
  • 重读正文并逐页检查可读性、裁切、页码和最终签名可见性；自动检查能证明的范围如实说明。
  • 把通过检查的文件与附件固定成可带走、可再次核对的版本，不覆盖旧版。
  • 把已生成、已签、可递送、已送出、已收到、已处理和对方签回分别报告。
  • 中断后先核对最近可用的包与现实记录，再从准确位置继续。

它不负责

  • 单文件编辑、只找原件和持续工作交付仍用各自入口，不为一次修改建整包。
  • 不靠旧路径、模糊文件名或程序日志猜当事事实与现实进展。
  • 代码通过测试、文件生成或电脑里有签名图片，都不等于已递送、收到或处理。
  • 对方签回不等于本人已签、款项已付或事项已解决。
  • 不自动发送、付款、撤回或联系外部对象，这些动作按具体授权处理。
  • 公开页不展示私人原件、签名图、回执正文或秘密值；可公开的产品状态和技术边界照常说明。
  • 不建立中央材料数据库、后台同步、服务队列或提醒中心。
  • 文书项目负责成品制作，工作或其他领域仍负责自己的业务判断。

产品思想与设计核心

01

已有合适入口就不绕路

只改单文件、只找原件或处理持续工作资料，各有现成入口；这里承接真正需要正式文书与附件包的事项。

02

整包固定不等于每句话都有来源

输入和附件能作为同一版保存，但目前仍不能自动证明每条事实都逐一来自哪份原件；重要说法要实际核对。

03

事实、未知和本人决定分开

原件互相冲突先说明，文字通顺不能让推测或尚未决定的请求变成已确认事实。

04

电子版与打印版共用内容

Word、PDF 和附件的意思相同；屏幕阅读需要清楚的彩色层级，确实要打印时再检查纸面与灰度，不强制每次做两版。

05

逐页查看是交付步骤

PDF 能打开，不代表正文、页码、裁切和签名都可用；最终签名位置与清晰度要看实际页面。

06

自动检查不替代整篇审阅

机器可以发现缺文件、字段或页面问题，不能保证整篇事实主线、语气和请求事项已审好。

07

本地签名只属于这一版本

一张签名图不等于电子证书、对方签名、可信时间或外部接收。

08

可递送还没有递送

接收对象、渠道和文件固定后才能说材料已具备递送条件；真正送出要另有动作证据。

09

现实进展逐级确认

送出、对方收到、实际处理与对方签回各有自己的来源，不能凭前一步推下一步。

10

材料包可复制核对，但没有自动备份

完整包能带到另一处重新验真；目前没有后台备份或可续传镜像，不把复制成功写成灾备完成。

当前缺口

  • 本轮没有读取真实个人材料、真实签名或现实回执，也没有执行真实制作与递送 E2E（端到端验证）；合成结果不能证明任一真实事项当前可完成。
  • facts[].source_note 仍是可选说明：当前可以固定整包输入，但不能机械证明每条事实分别来自哪份原件、本人陈述或其他依据。
  • 自动化能核对字段、结构、正文存在、页码、彩色/灰度页面、附件与哈希；DOCX 会匹配签名资产的精确哈希，PDF 只要求图像对象计数至少为 1，不能证明该对象就是签名、位置正确或最终可见。没有绑定 AI 或人工整篇语义审阅回执，也不能证明事实主线、语气和请求事项已经完整审过。
  • 通用 CLI（命令行工具） 没有实现 delivered、received、handled 或 counterparty_signed_returned；这些只由当前事项和现实来源推进。
  • 签名是规范图片资产与 SHA-256 绑定，不是证书签名、可信时间戳或对方同意证明；manifest（清单） digest 也是内容摘要，不是数字签名。
  • v3 release 可以完整复制到空目录后独立复验，但没有自动备份、后台恢复或可续传 mirror；2.0.0 的 v2 release 只按其历史实际携带内容验证并返回 non-self-contained 限制。

当前本地能力
严格输入经过 plan、build、verify 后生成 3 类同源成品：DOCX、PDF、附件包和对应逐页审计；当前通用 CLI（命令行工具） 只自动推进 produced（已生成）、signed（本人已签）与 ready_for_delivery（已具备递送条件），始终 delivered（已递送）=false。
能直接辨认的交付文件
通用文书按用途输出中文名，例如 正式说明.docx/PDF、合同协议.docx/PDF；附件使用 附件01_标题.扩展名，保留中文并替换 Windows 禁用字符，标题片段最长 80 字符。原件名称和字节不被改写。
本人背景与事实归属
相关共同背景按需取自个人理解库，可靠更正在当前任务回写；文书采用的字段仍绑定本次明确输入，父库更正不追改已签署、已递送的版本或历史证据。
当前完整性
v3 release 封存规范化输入、文档、附件、结构审计、逐页彩色/灰度渲染和所需签名快照；精确文件集合复制到空目录后仍可独立 verify。
现实状态
已生成、本人已签、已具备递送条件、已递送、已收件、已处理必须分别回读；对方签回是另一条独立事实，前一步不能自动推出后一步。
安装后虚构验收
隔离 wheel 的两个控制台入口均真实携带 Word 导出资源，并用 Microsoft Word + Poppler 完成完全虚构的 plan → build → verify；1/1 页彩色和灰度审计通过，材料包状态为已具备递送条件，但没有发生递送。

完整执行流程

  1. 1
    选对入口

    先判断是否只改单文件、只找原件、需要持续工作交付，或确实要形成正式文书和材料包。

  2. 2
    固定当前事项

    明确目标、接收对象、期限、现有版本、当前状态、必要原件和下一步。

  3. 3
    区分事实与未知

    核对参与方、日期、金额、附件和来源说明；缺失项不通过模板或模型补猜。

  4. 4
    形成制作计划

    检查严格输入，固定文书用途、输出类型、签名要求、附件、渠道和递送边界。

  5. 5
    生成同源 DOCX/PDF

    优先使用 Microsoft Word 导出固定版，缺失时明确使用本地 fallback（后备路线）；内部角色代码不进入对外正文。

  6. 6
    审计内容和页面

    重读所有输出字段，检查结构、页码、彩色/灰度页面、签名可见性和每个文件哈希。

  7. 7
    发布递送前材料包

    只有全部机械验收通过才形成 v3 release；build 与 release 都不可覆盖，ready 仍 delivered=false。

  8. 8
    现实动作另行回读

    递送、收件、处理和对方签回分别绑定现实来源；材料改变或中断时从新的 build 或最近核对 release 继续。

本页用到的名词

需要核对专业含义时，可以在这里查看它在 文书和材料制作 项目中的具体用法。

Current matter（当前事项）
围绕一个明确目标保存当前原件、已确认事实、未知、决定、状态、下一步和恢复点的可读记录。
Immutable build（不可覆盖构建）
由一个 build ID 固定的输入、DOCX/PDF、附件、审计和 manifest；同名构建不会被覆盖。
ready_for_delivery（已具备递送条件）
递送版本、对象、渠道、附件和指纹已锁定；它明确不表示递送动作发生。
Self-contained release（自包含材料包）
离开原 build 目录仍带齐输入、成品、附件、审计、逐页图和所需签名快照，可在空目录复制后独立核对。
Manifest digest（清单内容摘要）
对清单内容计算的 SHA-256，用于发现意外变化；它不是数字签名或恶意篡改防护。
Page read-back（逐页读回）
把 PDF 每页渲染为彩色和灰度图，检查页面数、墨迹、边缘、页码并把每页哈希写回审计。
counterparty_signed_returned（对方签回）
对方返回的完整签署版本及来源记录；它与本人签名、收件和处理状态相互独立。
Legacy v2（历史 v2）
2.0.0 形成的旧 release；新工具继续核对它实际携带的文件，但明确说明它没有 v3 自包含闭包。

系统里实际有什么

下面是当前产品组件，不是概念分类。每一项都对应真实文件、入口或验证链。

01
文书和材料制作 Skill

从自然请求选择最小产品路线和必要原件。

只在需要正式文书/材料包时进入；单文件、原件查找和工作交付直接分流。

02
严格输入与 plan

固定事项、参与方、收件方、渠道、事实、请求、附件和签名要求。

版本化 JSON schema（数据结构） 加日期、唯一 ID、普通文件和签名 profile 校验；输入只解析一次后规范化封存。

03
DOCX/PDF 生成器

从同一内容生成可编辑版和固定版。

A4 Word 文档优先用打包的无窗口 Word exporter；不可用时显式进入 ReportLab fallback（后备路线）。

04
内容与逐页审计

证明输出字段、结构、页码、彩色/灰度页面和签名图片未漂移。

DOCX/PDF 重新提取文字，Poppler 逐页渲染，彩色/灰度页面分别哈希并执行墨迹/边缘检查。

05
v3 自包含 release

冻结一个可独立核对的递送前材料包。

精确集合包含输入、文档、附件、审计、逐页图、签名快照和 build manifest（清单）；缺文件、多文件、路径越界或摘要不符都失败。

06
当前事项与现实来源

拥有递送之后的现实状态与对方签回。

本地 CLI（命令行工具） 不生成后三个状态；只有可保留的现实记录或本人明确说明才能推进。

6 层证据分别证明什么

Source（源码）

能证明：PRIVATE（私有） main b7d33e5f735bfd46fca241b5a3f33559f4068604 定义 2.0.1 的输入、生成、审计、签名和 v2/v3 verify 语义。

不能证明：不证明任何真实原件、真实签名、接收渠道或现实结果可用。

Focused tests（聚焦回归）

能证明：32 项通用文书回归覆盖四类材料、输入漂移、closure、灰度页、v2兼容、wheel资源和不可覆盖。

不能证明：合成 fixture 不能证明真实内容质量或外部动作。

Full repository tests（全仓回归）

能证明：2026-09-01 基线 526 项通过、6 项环境性跳过、101 个子测试通过；本轮只重跑通用文书 32 项，不宣称当前提交全仓已复验。

不能证明：跳过项、真实设备和外部平台仍需各自验收。

Installed wheel synthetic E2E（隔离安装虚构端到端）

能证明：2.0.1 wheel 的两个入口都携带真实资源，并用 Microsoft Word + Poppler 完成虚构 plan/build/verify。

不能证明：不证明离线依赖恢复、真实用户材料或外部递送。

Gallery（画廊）

能证明：一页完全虚构样张来自当前生成器，并已完成彩色/灰度逐页审计。

不能证明：不证明全部材料类型、真实签名或整篇语义已经由本人接受。

Real matter E2E（真实事项端到端）

能证明：若未来执行，可证明当前原件、语义审阅、签名、材料包和现实状态真实成立。

不能证明：本轮没有运行，因此当前状态是 not_run。

维护入口

formal-plan --request <request.json> --out <plan.json>

形成制作计划：核对严格输入并返回输出、签名和递送边界，不生成文书。

formal-build --request <request.json> --output-root <output> --build-id <id>

生成与逐页验收：生成不可覆盖 build；全部机械验收通过时再形成自包含 v3 release。

formal-verify --root <build-or-release-root>

独立核对材料包：只读核对清单、精确文件集合、哈希、内容、页面、签名和状态；v2 会明确返回历史限制。
