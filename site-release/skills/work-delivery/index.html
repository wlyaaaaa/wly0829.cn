工作支持与交付

让我把真实工作中的资料理解、沟通、方案判断、评审和交付放在同一个已有工作入口处理；需要持续来源关系时，再使用可追溯且口径一致的交付包。

已安装 / 工作支持已扩展 / 真实工作价值待验
产品用法技术与依据

先看怎么用

你不需要记住 Skill 名，直接说需求就行

什么时候用

  • 有具体真实工作事项，需要理解资料、准备沟通、判断方案、组织评审或交付结果
  • 本人选定 2–5 份资料并希望保留版本与来源关系；需要多种一致成品，或者本轮只要 PRD 但这些资料明确还会继续变化
  • 已有交付包需要沿原 ID 继续更新
  • 工作任务需要相关真实经历与协作取舍，或产生值得回写的本人认识

可以直接这样说

我可以说“看看这段需求沟通，帮我指出双方没说清的地方，再整理一份回信”。它先处理这次真实问题，不要求我凑三份文件建包；如果后续要维护不断变化的 PRD，才进入对应来源版本流程。

最后会得到什么

我拿到本次真正需要的解释、沟通建议、评审判断或文件。持续来源分支会另外说明覆盖、事实、冲突、质量、变更和实际产物；可生成六类正式文件不等于每次都要生成六类。

不适合这样用

  • 只编辑一次单个 Word、PPT 或表格
  • 没有用户明确选择来源就扫描目录、账号或旧对话
  • 学习、职业发展、求职或私人文书材料
  • 未经精确授权发送、发布、审批、建任务或修改外部系统

正常时

当前事项和所选材料足够时，直接产出需要的沟通、判断或文件；持续来源交付包只有关键事实和质量检查就绪才生成正式成品。

发现问题时

业务冲突、未知或来源过期会具体指出，未解决的部分保留待确认草稿；本人背景不会冒充业务证据。

入口不可用或证据不足时

读取或生成入口不可用时，保留已知资料和精确缺口，仍可做的沟通与分析继续，不新建替代工作系统。

从哪里开始

在当前 AI 对话提出真实工作事项、沟通、评审或交付需求。只有你选了会持续变化的来源并需要保持产物一致时，AI 才进入持续来源交付包。

需要准备什么

  • 眼前工作目标和相关材料、已知约束或待决问题
  • 持续来源交付时，选定 2–5 份会保留版本关系的资料，并说明要哪些一致产物或后续 PRD 更新

为什么需要这个能力

手工分别改需求文档、评审演示和跟踪表，很容易出现日期、负责人、范围、指标和验收口径互相矛盾。更常见的问题是来源改了，却没人知道哪些旧成品已经过期。

从需求到结果

1

先处理眼前真实工作：理解资料、准备沟通、判断方案、组织评审或交付结果。一次性问题和一次性单文件编辑直接完成，不强迫建立交付包。

2

本人先选定 2–5 份资料，并希望保留它们的版本与来源关系；需要多种一致成品，或者这次只要一份 PRD、但资料明确还会继续变化时，都可以进入交付包。只有本轮真正需要的格式才生成，内部编号、事实结构和请求由 AI 组织。

3

尽早给出已读覆盖、关键事实、冲突、缺口和拟采用结构。事实、假设与未知分别保留，只把真正需要你决定的业务取舍交回来。

4

关键目标、范围、异常或验收仍不清楚时保留草稿，不为了赶时间生成看似正式的文件。质量就绪后，只做这次要求的 Word、演示或表格，不让一份 PRD 等无关成品。

5

当前固定成果包括 PRD 正文、来源清单、追溯表、需求 Word、评审演示和执行跟踪表；不把尚未实现的项目计划或周报说成现成功能。

6

已有事项继续原交付包。来源变化后，能唯一找到的原文自动重新对应，只让消失、歧义或引用受影响的部分过期；当前影响范围到事实和整个成品，不能声称逐段自动修完。

7

较长处理会说明实质进展、阻碍与有依据的时间区间。事实确认后的文档构建有明确速度目标，但合成测试与机械秒数不证明真实工作已经提速。

8

目前没有交付包导出、数据库备份或跨机丢失恢复；需要外部发送、发布、审批或建任务时仍核对真实能力与精确授权。

失败时会怎样恢复

没有持续来源关系的工作问题

系统反应：不强迫建交付包或等待多格式输出。

恢复方式：按当前事项直接完成材料理解、沟通判断或一次性制品；没有具体事项时不虚构公司或任务。

关键事实没有来源或互相冲突

系统反应：只能生成待确认草稿，不能为了赶时间冒充正式交付。

恢复方式：立即列出冲突字段、两边依据和唯一需要用户决定的问题。

选定来源后来更新了

系统反应：重新对应仍能唯一确认的原文；找不到、对应不唯一或引用变了的旧成品会标为过期。

恢复方式：只让你处理本次新增的真实冲突，再沿同一交付包构建下一版；无关事实不用重确认。

用户只要一次单文件编辑

系统反应：不创建交付包，也不引入数据库和追溯流程。

恢复方式：直接交给对应文档、演示或表格能力完成。

同一事项已经有交付包

系统反应：不再新建第二份，避免事实和文件分叉。

恢复方式：沿原交付包继续更新，保留同一组来源、修订和历史。

关键事实或质量检查还没准备好

系统反应：可以保留预览和待确认草稿，正式 Word、演示或表格暂不生成。

恢复方式：先补目标、范围、事实、异常或验收；只有 Word 需求就只制作 Word，不强迫多格式。

正式文档制作入口暂时不可用

系统反应：保留已确认事实和预览，不把预览当正式 Office 文件。

恢复方式：修复现有制作入口后，用同一份事实修订重新生成；不另装一套工具。

外部发送、审批或建任务未授权

系统反应：只交付本地文件和明确下一步，不执行现实外部动作。

恢复方式：复用当前请求或长期明确授权已覆盖的精确对象、内容和动作，并核对项目已验操作；新增目标、动作、范围或效果边界时才确认，执行后回读。

处理较久，还没有有用进度

系统反应：先说明已读多少、哪些事实和冲突会影响决定，而不是只报正在运行。

恢复方式：根据资料长度、输出规模与当前进展给有依据的下一检查点；完成时间须用同质量实际工作比较，不虚报节省。

对应项目工作支持与交付项目

这个 Skill 用到的名词

工作支持
资料理解、沟通、决策、评审和交付都可进入既有项目；交付包只是需要持续来源版本关系时的一项能力。
共用本人背景
按个人理解库合同读取相关真实经历和取舍，有依据新本人信息在同任务回写；业务事实仍来自本人选中的工作资料。
交付包
围绕一个持续工作事项组织的来源、事实修订版、交付物、追溯清单和变更影响；不是把文件简单放进同一文件夹。
work-delivery.batch.v1（批量新建请求）
一次提交 package ID、标题、目标、2–5 份来源和所需产物；避免每份来源或事实各启一个进程并重复登记。
Package ID（交付包标识）
新持续事项使用的稳定非空身份；已存在时必须走更新命令，重复新建会显式失败。
quality.status=ready（质量已就绪）
来源、事实、范围、异常、验收和关键冲突均达到正式构建条件；只有这一状态允许启动 Office builders。
SourceSnapshot（来源快照）
用户明确选入的一份资料在某个时点的不可变内容和指纹；来源后续变化会生成新版本，不覆盖旧证据。
EvidenceSpan（证据片段）
事实在来源中的精确段落、单元格或其他可回到原文的位置。
Fact revision（事实修订版）
一组已经确认的事实、明确假设、冲突和未知；所有正式产物必须说明自己使用的是哪一版。
ChangeSet（变更影响）
比较来源新旧快照后，列出受影响事实和已经过期的构建；它不是简单的全文重写。
ArtifactBuild（产物构建）
从同一事实修订版生成的一次 PRD、评审材料、执行表和追溯文件组合。

专业定义

真实工作中的资料理解、沟通、决策、评审和成品交付，先在现有项目选择最有用的做法。本人选定2–5份资料并希望保留版本与来源关系后，还须满足二者之一：需要多种一致成品，或者本轮只要PRD但资料明确还会变化，才进入持续来源交付包；一次性问题与文件直接完成。

执行参考

下面保留 AI 和工具实际使用的参数、步骤与依赖。日常使用可以直接提出需求，不需要先手工准备这些协议。

输入

  • 普通工作支持先接收具体事项、当前沟通和已有材料；只有持续来源交付包分支要求2–5份明确来源
  • 持续交付包分支：用户明确选择的 2–5 份需求、会议记录、规则、表格或其他工作资料
  • 持续交付包分支：新持续事项的稳定且非空 package ID、标题和目标；已有交付包使用原 ID 进入更新命令
  • 持续交付包分支：每条候选事实或假设的值、类别、原文证据、动作和非空决定理由
  • 持续交付包分支：本轮实际需要的 docx、pptx、xlsx 格式；只要 PRD 时只请求 docx

输出

  • 普通工作分支直接交付这次需要的解释、沟通建议、决策或评审判断，无需先建立交付包
  • 来源覆盖、已确认事实、假设、冲突、未知、质量状态和唯一待决定事项
  • PRD.md、manifest.json、traceability.csv、产品需求文档.docx、项目评审.pptx、执行跟踪表.xlsx 中本轮实际请求且质量允许的文件
  • 来源变化后的自动重新绑定、过期事实、过期 build 和下一版决定

执行顺序

  1. 1

    先明确实际工作问题，按项目 AGENTS 选择资料理解、沟通、决策、评审或制品路径；不把所有问题强制做成交付包；交付包入口同时要求本人选择2–5份来源并保留版本/来源关系，以及多种一致产物或本轮只要PRD但资料明确继续变化。

  2. 2

    需要本人通用背景时按个人理解库 DOMAIN_CONTRACT 读取相关内容；有依据的新认识在当前任务回写并回读

  3. 3

    读取项目当前 AGENTS.md 和稳定入口，不在 Skill 里复制实现

  4. 4

    新持续 PRD 使用一个 work-delivery.batch.v1 请求提交 package ID、标题、目标、2–5 份明确来源、证据事实和所需格式

  5. 5

    尽早交回来源覆盖、关键事实、冲突/缺口与拟采用结构；较长处理或外部等待时给出有依据的区间 ETA（预计完成时间）或下一检查点

  6. 6

    把事实、假设、冲突和未知分开，只让用户处理真正需要决定的项目

  7. 7

    只有 SQLite 重建的 canonical manifest（清单） 报告 quality.status=ready 才调用正式 Office 构建；手写 ready 被拒绝

  8. 8

    只要 PRD 时只请求 docx，不等待或启动 PPTX/XLSX

  9. 9

    已有 package ID 通过 update-source、impact、review、build、verify 和 artifacts 继续

  10. 10

    来源更新时唯一原文自动重新绑定，消失或不唯一的事实和引用变化的旧 build 才过期

操作边界

  • 一次性单文件或无持续来源关系的普通文本 PRD 直接使用现成文档、演示或表格能力，不增加交付包
  • 当前正式输出只有 PRD.md、manifest.json、traceability.csv、产品需求文档.docx、项目评审.pptx、执行跟踪表.xlsx；没有现成项目计划、周报或汇报
  • 可靠输入仍以本地文本、Markdown 和 CSV 为主；其他格式先由相应能力读取或导出
  • AI 分析在项目外，Skill 与项目核心都不内置模型或扫描器
  • 普通 2–5 份来源尽早给出覆盖、关键事实、冲突/缺口与结构；较长处理或外部等待时按资料长度、冲突、输出与进展给出有依据的时间区间或下一检查点；最终时间按同模型同质量直接基线判断
  • 事实确认后的确定性 PRD.md + DOCX 目标不超过 15 秒；机械时间不冒充整个工作提速
  • 缺目标、范围、需求、异常、验收、证据或存在关键冲突时，quality 不得 ready，正式 Office builder 保持 0
  • 没有交付包导出、SQLite 备份、数据库丢失恢复或跨机器迁移
  • 外部发送、发布、审批、建任务、邀请和修改复用当前请求或长期明确授权已覆盖的精确目标与动作，并要求项目确有已验证操作；出现新的目标、动作、范围或效果边界时才确认
  • 共同本人背景不能冒充已确认业务证据；工作事实、交付状态与专业判断留在工作项目，不另维护本人档案
  • 没有具体事项时不虚构公司、职位、任务或预建台账

依赖

  • PRIVATE（私有） work-delivery-copilot 项目
  • work-delivery.batch.v1 规范请求
  • 现有文档、演示文稿和电子表格运行时作为正式产物构建依赖
