电脑卡顿、当前健康与内存证据

电脑刚卡顿、想看 TimeAudit 现在是否正常，或需要一段内存与硬件历史时，AI选择对应只读入口。你描述症状和时刻，就能得到实际证据、可能原因与缺口。自己用了哪些应用、看了多久屏幕则由个人活动查询回答。

历史查询有带日期的真实使用记录；综合卡顿、当前健康与原生内存入口已在发布原文确认，但本次没有运行，不能据这页判断电脑此刻正常。
产品用法技术与依据

先看怎么用

你不需要记住 Skill 名，直接说需求就行

什么时候用

  • 刚刚发生卡顿、冻结或响应迟缓，需要把历史、原生内存和 Windows 事件对到同一时段
  • 询问 TimeAudit 当前组件、原生日志、备份与最近自动恢复结果是否健康
  • 想按一段时间查看处理器、显卡、内存、磁盘、网络或游戏画面的历史变化
  • 只想看 Windows 已保存的内存记录，或确认那段时间有没有记录

可以直接这样说

“刚才电脑卡住了，别重启，先看看那十几分钟有什么证据。”AI把同一时段的历史、原生内存与Windows事件放在一起，保留每条来源的空档，不拿现在正常反推当时没事。

最后会得到什么

得到有时间边界的诊断、当前组件健康或 Windows 已保存的内存记录，知道哪一层实际读到、哪些只是候选原因。此能力只观察；修复与真实效果另走对应项目。

不适合这样用

  • 要自动启动、停止、修复或重新配置采集器和服务
  • 要通过这个聚合入口读取活动正文、逐进程明细或原始事件消息
  • 把一次峰值、调度抖动或最大进程直接当成根因
  • 把过长的历史拆成大量查询来绕过读取上限
  • 查询本人应用或屏幕使用总量；该问题走个人理解库的活动事实入口

正常时

相关来源和时间范围核对成立时，交回实际健康、聚合和有依据的下一步。

发现问题时

一条来源降级或历史有空档时保留其缺口，其他独立证据仍可使用；相关性不升级为根因。

入口不可用或证据不足时

入口或记录不可用时，只停止依赖该来源的判断，继续适当的其他诊断，不自动重启或配置机器。

从哪里开始

在当前 AI 对话说‘刚才电脑卡了’、‘现在 TimeAudit 正常吗’，或指定一段性能历史和指标；AI 会选相应只读诊断入口。问自己用了什么应用或看了多久屏幕，则走个人活动查询。

需要准备什么

  • 症状与大致发生时间；历史问题尽量给出时段和关注的现象
  • 只问当前健康、开销或原生内存记录时说清是哪一种，无需提供日志路径

为什么需要这个能力

当前任务管理器解释不了过去，历史摘要也不能证明现在健康；不同记录没有对到同一时间，容易把缺数据或相关峰值当成根因。

刚卡顿时对齐同一时段的证据

刚才电脑卡了十几秒，能看出什么吗？

说出症状和大致发生时间即可；AI 选择最短够用的时间窗。

AI 把已保存的性能历史、Windows 事件和内存记录对到同一时段。最近事件可另外看现在的状态；旧事件不会拿此刻的正常状态代替当时。

你会知道哪些证据支持一种可能解释、哪些反对或缺失，以及最值得继续检查的一步。

峰值或同时发生的事件只是线索，不自动算根因。历史范围和读取量有上限；记录被截断就明说，不通过反复查询绕过。

确认记录工具现在是否正常

TimeAudit 现在正常吗？会不会自己太占资源？

说明是问当前健康，还是还想了解它此刻的资源开销。

AI 检查采集组件、最近留下的日志、备份和上次自动恢复结果。只有问开销时，才额外做一次短时测量。

你会得到具体哪部分正常、降级或无法检查；问开销时也会看到测量覆盖了哪些进程。

程序还在运行或端口能连接不等于采集健康。短时开销未覆盖所有独立组件，查不到的进程不能写成零开销。

回看一项历史指标

昨晚游戏卡的那段，帧率和机器负载是什么样？

给出时段和关注的指标，不必自己写数据库查询。

AI 先看那段是否真的有记录，再解释有效的处理器、显卡、内存、磁盘、网络或游戏画面更新数据。

你会得到带时间范围的变化和实际样本数量，也会看到资料不足以回答的部分。

没有游戏画面数据可能是没在运行游戏，也可能是采集失败；温度或电力没有记录不能写成零值或正常。

只检查内存相关记录

只看电脑内存记录有没有覆盖刚才那次卡顿。

发生时段，或直接说只想看记录覆盖。

AI 只读已有的系统内存记录，把实际覆盖与同一采样时刻的内存压力放在一起。

你会知道那段时间是否连续有记录、有哪些内存信号、哪里是空档。

一段记录横跨该时间，不等于每时每刻都有样本。单个最大进程或一项抖动也不足以认定卡顿原因。

失败时会怎样恢复

历史入口不可用、记录过旧或没有数据

系统反应：停止使用这份历史输出，不把空结果写成无异常。

恢复方式：继续普通 Windows/驱动/任务诊断；只有用户要求修 TimeAudit 时才交给负责该项目的任务。

游戏画面数据缺失或前后不一致

系统反应：不凭这些数字判断游戏性能，说明有多少样本不可靠。

恢复方式：只有确实记录到有效画面时，才解释帧率和每帧耗时；否则保留采集缺口。

看到一个超过阈值的信号

系统反应：报告发生时段和次数，把它当线索，不直接点名根因。

恢复方式：按这次问题选一项相关的现场证据交叉核对，避免无关的整机扫描。

用户要求逐进程、路径或窗口明细

系统反应：说明当前 v1 仅聚合，不能从缺失字段猜答案。

恢复方式：字段本身不是天然敏感；有真实需求时走另一个明确、可控且按实际值判断敏感性的路线。

这个 Skill 用到的名词

Bounded window（有界时间窗）
一次只查询能改变当前判断的最短历史区间，最长 168 小时；避免把数据库当搜索引擎遍历。
Coverage（覆盖质量）
说明请求窗口是否 fresh、stale 或 empty，并列出样本数、最新样本年龄和最大空档；没有覆盖不等于电脑健康。
Aggregate-only provider（仅聚合接口）
用一次固定查询返回范围、均值、峰值、时长并集和出现次数，不返回逐行历史；这是速度与语义边界，不是字段类别的公开禁令。
Correlation-only（只表示相关）
某信号与问题发生在同一窗口，只能作为候选线索；还要结合实时状态、Windows 事件、驱动、任务或 PCConfig 才能判断原因。
No game frames（没有有效游戏帧）
该窗口没有可用的正 FPS 样本；可能当时没运行游戏，不能写成掉帧或采集故障。
Uncovered seconds（未覆盖秒数）
请求窗口减去已记录状态并集后的时间；可能是睡眠、关机或采集空档，不能单靠它区分。

专业定义

刚刚卡了一下、想知道 TimeAudit 现在是否正常，或需要回看一段内存和硬件记录时，AI 会选择对应的只读入口，把同一时间窗的证据、当前状态和缺口分开。本人用了哪些应用或看了多久屏幕由个人活动查询回答，不由性能采样推算。

执行参考

下面保留 AI 和工具实际使用的参数、步骤与依赖。日常使用可以直接提出需求，不需要先手工准备这些协议。

输入

  • 症状、发生时刻或尽可能窄的时间范围；具名时段使用带时区的起止
  • 要看当前健康、历史指标、综合事件，还是只看原生内存证据
  • 确需测量采集器自身开销时明确这一问题

输出

  • 同一请求时段内 TimeAudit、原生内存和 Windows 事件的独立状态、聚合与缺口
  • 当前健康的组件、封闭原生日志、备份和最近watchdog结果；可选两秒采集器开销
  • 精确历史窗口、样本、内部空档、有效游戏帧及不可用测量
  • 实用诊断结论、候选原因与下一项有依据的检查；root_cause_established=false保持明确

执行顺序

  1. 1

    先按问题选择综合事件、当前健康、单项历史或原生内存入口

  2. 2

    核对返回schema（数据结构）/owner、实际时间范围、隐私标记、来源状态和evidence_gaps

  3. 3

    分别解释当前样本与历史覆盖；局部来源不可用时保留其他有效来源

  4. 4

    以实际聚合支持候选原因，交回关键证据、反证、缺口与下一步，不执行修复

操作边界

  • TimeAudit 只是可选历史证据，不单独证明根因
  • 单次窗口最多 168 小时，不网格化暴力查询
  • provider 为速度与语义稳定只返回聚合；进程、路径、标题等字段类别并非天然敏感，可由其他合适路线在有价值时使用
  • 不调用 Grafana、db_audit、PCConfig cursor 或采集控制入口
  • provider unavailable/stale/empty 时回到普通诊断，不把缺数据写成健康

依赖

  • E:\PCConfig\tools\Get-ComputerStutterDiagnostic.ps1
  • E:\Projects\Tools\TimeAudit\timeaudit_health.py 与 timeaudit_diagnostic_summary.py
  • E:\PCConfig\tools\Get-MemoryFreezeEvidence.ps1
  • TimeAudit 的 TIMEAUDIT_DIAGNOSTIC_SUMMARY_CONTRACT.md、DIAGNOSTICS_OPERATIONS.md；PCConfig 的 docs/recovery/memory-freeze-diagnostics.md

四条入口及其各自结果

综合结果接受pcconfig.computer-stutter-diagnostic.v1，owner=pcconfig:computer-stutter-diagnostics，status为ok/partial/unavailable。核对请求窗口、逐来源状态、所有隐私标记和assessment.evidence_gaps；root_cause_established=false是设计边界。

明确窗口同时传AfterUtc（不含起点）与UntilUtc（包含终点），时间必须带时区；SkipLive跳过当前快照，旧事件会自动跳过。原生段与事件读取也有限额，截断不得称覆盖完整。

# 综合卡顿诊断
& E:\PCConfig\tools\Get-ComputerStutterDiagnostic.ps1 -Minutes 15 -Json
# 具名历史时段
& E:\PCConfig\tools\Get-ComputerStutterDiagnostic.ps1 -AfterUtc <带时区起点> -UntilUtc <带时区终点> -SkipLive -Json
# 当前完整健康
& E:\Projects\Tools\TimeAudit\.venv\Scripts\python.exe -B E:\Projects\Tools\TimeAudit\timeaudit_health.py
# 历史指标
& E:\Projects\Tools\TimeAudit\.venv\Scripts\python.exe -B E:\Projects\Tools\TimeAudit\timeaudit_diagnostic_summary.py --hours 3
# 原生内存事件
& E:\PCConfig\tools\Get-MemoryFreezeEvidence.ps1 -Minutes 15 -Json
# 仅原生内存覆盖
& E:\PCConfig\tools\Get-MemoryFreezeEvidence.ps1 -CoverageOnly -Json

健康、开销与历史不能互相替代

timeaudit.runtime-health.v1 / timeaudit:runtime-health的degraded和退出码2是有效诊断结果。--core-only比完整健康窄；--include-overhead只追加两秒、精确主采集器及子进程的测量，RSS相加不等于独占物理内存。PID存在或端口打开不证明采集健康。

历史入口接受timeaudit.diagnostic-summary.v1 / timeaudit:diagnostic-history，支持--after-utc/--until-utc；检查bounds、coverage、gaps、counts与隐私标记。原生内存接受pcconfig.memory-freeze-evidence.v1 / pcconfig:memory-freeze-diagnostics；读取器在Windows PowerShell内聚合后才跨兼容边界，反序列化计数器字符串不是日志损坏。

fresh只证明覆盖请求终点，仍须检查内部空档；rolling_coverage与旧会话尾段分开。System_CollectionGap不是已经证明的睡眠，挂起/恢复、锁屏和熄屏含义不同。FPS、平均FPS和单帧时间也不能互换。调度抖动不是内核 DPC/ISR 延迟，最大进程或绝对池大小也不能直接指认根因。

失败、范围与证据日期

一个Provider无效、缺失或超时时舍弃它的输出，其他独立来源仍可使用；不反复重试或扩大到原始活动记录。此入口不调用db_audit.py、Grafana或Invoke-TimeAuditAnomalyIncrement.ps1，不启停采集器、任务、Docker、网络或电源。

历史备份清单核对不等于本次全文件hash（内容指纹）或新的恢复演练。页面原有2026-08-31与2026-09-08记录保持原时间；本次按已发布 Skill e734251 对齐职责边界，综合健康与原生内存入口没有在本次网页任务运行。
