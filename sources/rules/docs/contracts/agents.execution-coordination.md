# 分工与并行施工

owner: `E:\.agents`

这里是 Codex 和 Claude 共用的分工原则：要不要派子代理、怎么派、多个任务同时改东西时怎么不互相踩。两个宿主各自的调用方式只在各自适配专题里补充几行。

## 派子代理的原则

1. **主持的想和把关，活派出去做**（约法 L22）。主持的根会话管战略、头脑风暴、抽查、QA 和最后以人的角度看成品；具体的活派子代理做完、把结果送回来看，哪怕自己做也很快。只有整段活一两步就完的小事（看一个文件、改一句话、记一条本人决定）顺手做：看整段的目的和总量，不看单次操作多容易，50 张截图不是 50 件小事。相关的动作合成一单、一次交代清楚，不一个点击派一次。0 个子代理也正常：整件事只需要判断，或者本来就一两步。
2. **按成品的要求和公开数据选人，能胜任的最低一档就够。** 能用就行的交能胜任里最划算的；要惊艳的，样板和关键部分交做得最好的，其余照样板铺开；机械活交最便宜的。开工前在计划里写明这件成品算哪一类：会被人直接看到、用到，好坏只能靠人眼判断的算要惊艳；能靠测试、报错判断好坏的算能用就行；本人随时可以改。谁能胜任、谁做得最好，只以厂商公布的数据和 AA 等权威评测为准，不在本机试跑比较，本人说的强弱也不作依据（约法 L22）；现在的选择和依据见模型清单 `routing`，它是按数据得出的，不是固定身份。档位按这条支路剩下的真实难点选，质量需要时可以比根会话更强，不用逐次问本人。
3. **别浪费额度。** 算未来的总投入：自己做要花的执行、验证和返工，对比委派要花的交代、上下文重建、来回沟通、审阅集成和返工。已经花掉的不算。
4. **每次都显式写出型号和档位。** 不让子代理悄悄继承根会话的设置，派完核对实际启动的型号和档位。GPT-6.1 Sol 子代理默认统一用 ultra，不再按任务难度挑 high 或 xhigh；GPT-6 Luna 没有 ultra，按其可用最高档 max 派，只有照写好的提示生图、落盘例外，用 low（见模型清单场景表“生图”）；Astra 有 ultra，仍按已有授权和模型清单选择。当前 GPT-6.1 Sol、GPT-6 Astra 的 xhigh 派单统一用 ultra；GPT-6 Luna 用 max。ultra 是允许子代理的 xhigh，不是比 max 更高的档位。Claude 自己的档位按模型清单选择；这些档位默认限当前具体型号；换代时按约法 L23 和下面“新型号怎么调研”重新评估、直接更新，不自动沿用旧型号的设置（出处：`docs/owner-decisions.md`“GPT xhigh 统一改派 ultra”“Sol 默认 ultra、Luna 最高档与前端审美判断”“当前代际的模型判断与档位规则”）。
5. **重大的事要独立复核**（约法 L22）。重大的改动、设计或决定，交给一个独立的上下文重新检查：给复核者原始材料（本人原话、相关事实、改动本身），分清本人原话、已核事实、未知和父代理的推断，不预设结论，让它先独立形成意见。复核者给证据、反例或失败路径；没有实质问题就直说，不为凑问题改东西。复核按需要做，不让每一步都变成审批。它和重大动作前的“把关”不是一回事：把关只管动手前这一步做不做、要不要请本人验证（见[重大动作与本人验证](agents.protected-actions.md)）。
6. **一次交代清楚。** 写明目标、已知事实、限制和怎么验收，用中文、说人话；不灌全部历史，也不替子代理写死每一步。子代理能自己查的自己查；遇到关键事实冲突或超出范围的决定，带着证据回来问。交付时分清已核实的事实和推断，带上结果、实际验证、实质反证及未解决风险；型号名称和“同意”都不证明正确。
7. **全局规则只引用、不改写，资料锁着时不凑。** 派活说明和项目说明里，公开范围、个人资料锁、授权这类全局规则只写引用，例如“公开范围按约法 L20 和《个人资料与数据处理》的公开分级表”“资料按约法 L18”，让子代理读原文；不写自己的摘要或改写版，也不照抄决定记录里的旧说法，旧决定可能已被取代，以现行规则为准。要写成公开内容（网站、GitHub 主页、公开仓库、对外发布）的，交代它先读公开分级表原文再判断。子代理需要本人私人资料而资料锁着时，不让它用已记下的事实凑，也不收降级的结论：它写明缺什么交回，根会话按约法 L18 请本人验证、解锁后再派。只为举例不算需要：公开内容里的例子可以是假设的或直接用亮点，不为找真实例子读私人资料，假设的例子也不写成真发生过（决定：9 月 29 日 00:0x“网站：例子可以是假设”）。派活说明里固定写这一句：“需要本人私人资料而资料锁着时，只写明缺什么交回，不用已知事实凑、不降级回答（约法 L18）。”
8. **本人的限制优先。** 本人明确限定的型号、厂商、档位或预算，子代理和后代都照样遵守，不能自己放宽。子代理的业务范围和授权只能比父代理窄（见[用户授权](agents.authorization.md)）。
9. **可派范围看模型清单。** `config/model-roster.json` 列出各宿主现在能派哪些型号、各适合什么活。它只作参考，不当门禁；更新和本人已定的型号限制以约法 L23 为准，新型号按下面“新型号怎么调研”查。项目专用分工只在对应项目内适用，不自动改成全局默认。
10. **接力做一样成品，要有一个人对整体负责。** 几段接力做同一个成品（例如写、画、审、拼）时，由根会话或指定的一个负责人对最终成品负责，亲自看它在真正被使用的地方的整体（截图、录屏可以派人在真实环境里采好送来）：比例、版式、空白、前后是否一致。各段的自查只管自己那段，替代不了成品验收。先做一个从头到尾的完整样板定下规格，再批量做；几段共用的规格（尺寸、字号、版式、禁令）只写一处，各段引用（决定：9 月 29 日 04:2x“接力做成品要有人整体看”）。

根会话负责战略、优先级和最终验收（约法 L22），要惊艳的样板和关键部分可以亲手做；派出去后继续做不冲突的事，不空等。创建成功只说明任务已经发出，不说明做完了；子代理的结果由根会话核对。本人叫停主任务时，一起停掉已知的子代理。

Claude 主持、和 GPT 协作时，按约法 L22 和模型清单：Claude 想和把关，也亲手做模型清单里交给它的要惊艳的样板和关键部分；本人定过由 Claude 写的（给本人看的成品和分析、网站文案、正式法律文书、对本人价值和偏好的理解）照旧。施工、采集、按清单审查和核对其他执行者的汇报，按场景表派出去。GPT 审查时，清单外的实质问题也要提；请 GPT 出主意时，给原始材料和没定的问题，不先把 Claude 的结论写成答案。抽查时 Claude 定看哪些风险，GPT 交完整的材料清单，Claude 也可以自己挑没被推荐的样本。只用一边时那一边全做：本人说 GPT 额度少，Claude 自己施工；本人说 Claude 额度少，Claude 判断是等额度重置再做，还是抽查后认为现在就可以；只用 GPT 时，GPT 的主对话把关，要惊艳的部分交模型清单里 GPT 这边最合适的型号或自己做；公开评测确实显示另一家更合适、又会影响结果时，交付时说明差别和数据缺口，没有匹配的数据就只说缺口。独立 Codex 主持的任务由当前根会话承担同样的最终责任，不把历史分工当成必须等 Claude 的理由。不为选型检查本人全部账号额度。Claude 派 GPT 的具体入口见[Claude 适配](agents.claude-adapter.md)的“派 GPT”。

未经本人许可，不启用 fast 快速模式。故障后先核对并接回被打断的任务，排查可以另行并行；需要等真实额度恢复的任务，恢复后在原对话继续，并告诉本人额度已恢复、任务已继续，不为恢复额度重建替身。同一 Codex 额度下根会话仍能正常工作、只有子代理报额度耗尽时，按下面的规则立即接续。需要更换上下文时先核对原任务的真实状态，交接或停止后再安排，不重复执行。

新开一个顶层任务（新对话）只在确实有独立的成果和责任时才做；项目多、工作量大或空槽满了都不是理由。AI 新开的顶层对话默认不挂到任何已保存项目下，本人指定项目时除外。

## 做错了怎么办

升档、换人只看根会话验收看到的事实，不等子代理自己说不够：没有哪个模型会说“我推理不够”。

- 缺材料、交代漏了、工具出错、执行者中途断了：补上，在原线程、原档位接着做，已有的有效结果照用。这些不算做错。
- 有明确的错，也知道怎么改：把反例和验收要求退回原执行者，改相关部分，不从头重做。
- 纠正后还犯同一个关键错误，或者核心方案被反例推翻、执行者拿不出能满足要求的改法：换人。可以换同一家更强的型号（例如 Sol 换 Astra），也可以换另一家（Claude 和 GPT 之间才算换一家）；交代剩下的难点、失败证据和已排除的原因。
- 开工后发现活比原来判断的难：当场按剩下的活重选型号和档位，不用等失败。
- 两家都做不对：最后用一次 max，写明要解决哪个难点、怎么验收；还不对，能自己继续修的照常修，剩下的带着结果、证据和可选做法来问本人。同一个模型不把从 xhigh 加到 max 当默认的下一步：两档只差多想一会儿，评测分数不一定更高，还更慢（见模型清单 `routing.effort_rule`）。
- 只缺本人才能给的材料、取舍或授权：不等失败次数，整理好直接问本人。

## 原生容量不足与原线程接续

这里是共用执行规则；Codex 的入口差异和命令见[Codex 适配](agents.codex-adapter.md#原生容量不足时转用共用包装器)，Claude 的默认调用见[Claude 适配](agents.claude-adapter.md#派-gpt)。（出处：决定文档“Codex 满槽派发与同额度子代理续作”）

- **容量够用时优先原生，真满槽才自动转用。** Codex 按当前宿主实际可用容量和任务状态判断，计入仍占槽的后代，不写死槽数。只有明确容量不足才能转用现有 GPT 包装器；鉴权、参数、上下文、网络或能力限制等失败先按真实原因修复，不一概当满槽。原生派发回执不明时，先查代理列表、任务状态或宿主回执，确认有没有实际启动；已经启动就接回原任务，避免重复执行。
- **入口改变，范围沿用。** 转用包装器仍是当前根对话管理的后台子任务，不建立顶层替身；显式选现有可派型号和档位，不扩大父任务的型号许可、业务范围、授权或期限。包装器保存 `ParentHarness`、完整 `SessionId` 和 `ContinueOnQuota`，后续 Resume 沿用。
- **同额度子代理单独报耗尽时立即原线程续作。** 仅同一 Codex 额度下根会话仍可正常调用、子代理报额度耗尽时适用，不等额度恢复。原生 GPT 子代理用原代理的 followup（续作）入口，其他公司模型主持的原生 GPT 子代理用原 `openai_child`；包装器任务启用 `-ContinueOnQuota` 后立即在同一线程续作，后续失败短暂退避再试，并持续受本轮时限约束。不得用 Start、新代理或新顶层对话替代旧任务。真正共同耗尽或无法确认根可正常调用时，保留原任务和状态，按实际恢复时间等候；Claude 默认不启用该开关。登录、参数或上下文出错时，修好真实原因后接回原任务，不乱换型号。
- **一直有人管理到交付。** 包装器 Start、Resume 的返回只表示本次等候结果；`still_running=true` 时立即照返回的 `watch_command` 挂后台 Watch，同一任务同时一条，每次返回后仍在跑就重新挂。需要时 Status/Check 核对真实状态，运行中纠偏用 Steer；截止提醒时还在有效推进就 Extend 延长，然后继续 Watch。原生任务用本宿主的查看和等候入口持续跟进。根会话继续做不冲突的工作，不能因后台还有任务就结束整个主任务。
- **停止与验收由根负责。** 本人叫停主任务时，停止全部已知原生任务、后代和包装器任务；停止等候命令不证明任务已停，要回读状态。执行者消失时先看已有改动和汇报，再在原线程 Resume。终态读取本轮 `report.md`、`last-message.md` 并核对实际成果和验证，不能把启动、入队、子代理自报完成当最终验收。包装器任务成功或主动停止后的会话清理沿用[Claude 适配的清理规则](agents.claude-adapter.md#派-gpt)。

## 新型号怎么调研

本人会告诉 AI 有新型号或新档位发布了，AI 就照这个办法查、按需更新模型清单并直接生效（约法 L23）；本人要求重估分工时也照这个办法查。AA 等权威评测还没出数据时，先按厂商公布的评测数据暂定，在模型清单里标“暂定”；厂商数据已经够判断的（例如同一家的新一代旗舰明显更强），直接定稿。本人说 AA 出了数据时，对这次新型号相关的选择做一次短复核：结论变了就改，暂定的核实后去掉“暂定”。模型能力（会不会做、做得好不好）只以厂商公布的数据和 AA 等权威评测为准，不在本机试跑比较，本人说的强弱也不作依据（约法 L22）；运行上的事实（宿主支不支持、派出去实际是哪个型号、多慢、会不会卡住）照实际使用记录。要找的是每类活能胜任的最低一档：先能胜任，再更快，再省额度。结论落到模型清单 `config/model-roster.json` 和两个宿主适配的用法。

1. **身份和可用性。** 从官方发布页、模型文档和价格页查型号 ID、价格（输入、输出、读缓存）、上下文、有哪些思考档位、默认哪档；在新开的对话里核对宿主能不能派、派出后系统提示里写的实际型号。
2. **先弄清分数量的是什么。** 以 AA 为主，按档位、按场景看：每个评测的题长什么样、分数怎么算，对应本人哪类活（模型清单 `routing.evals`）。分数是在很难的题上比高低，不是日常活的成功率；各档位分开看，最高档的分数不能给低档作证。评测页把分数、花费、耗时嵌在页面数据里，图上读不出时用浏览器从页面数据读；取不到的说明缺口。花费只在同一家里比，两边订阅额度各自独立。
3. **和现在的选择比。** 同一类活的相关评测上，新型号或新档位不低于现在的选择、耗时不更长，就可以换上；能胜任之上的分数只换来多等、多花。要惊艳的活看成品质量和审美类的评测（例如成品两两盲评、网页设计的人类偏好榜），不只看编程分。
4. **第三方评测和社区反馈。** 只采用有方法、有样本的评测；每条写来源、日期、样本多大、可能的偏差；厂商公布的评测数据可以作暂定依据，没有数据的宣传说法只当线索。互相矛盾时写明怎么判断，推断标明是推断。
5. **落地和记录。** 完整数据连同出处和查询日期写进决定文档对应一节；模型清单只写选择和起决定作用的几个数，注明查询日期。模型路由（哪类活派哪个型号、用什么档位）按数据直接更新；授权、预算这类本人定过的事要变先问本人（约法 L23）；都写清依据和怎么撤回。新型号的实际派出核对列进待验收清单。

改分工的快做法：
- **只改分工数据**（哪类活派哪个型号和档位、场景表、依据、不派的理由、新的 Claude 子代理模板）：改 `config/model-roster.json` 和 `templates/claude-home/agents/`，完整数据写进决定文档；跑 `agents-charter`、`agent-runtime-compatibility`、`duplicate-content` 三项测试，合并推送并快进活动检出 `E:\.agents` 就生效。这些文件不在规则发布快照里，各会话直接读主分支，不用发新版本；新的子代理类型在定义重新加载后出现（已开的对话也会，9 月 29 日实测），派一次核对实际型号。
- **改规则文字**（分工的做法、这套调研办法、各专题里的说法）：按[规则发布](agents.rule-release.md)选快速发布或标准发布；快速发布入口的 `-Mode Inspect` 会说明这些文件走不走得了快速通道。
- **发布后**：回读活动版本；通知正在派活的会话，只说改了什么、从哪一版起。

## 多个任务同时改东西

- **各用各的工作副本。** 每个任务在自己的 git 工作副本（worktree）里改，完成验证后自己合并回默认分支并推送；合并时遇到冲突，先理解对方的改动再整合，不覆盖。合并推送并回读之后，把计划任务或技能直接在用的活动检出（例如 `E:\.agents`、`E:\PCConfig`）快进到最新；活动检出里有别人没提交的改动、不能快进时，不动它并说明。最后按[工程与交付的清理入口](agents.engineering-delivery.md#下载临时文件和清理)，用 `Move-TaskItemToRecycleBin.ps1 -AllowLinkedWorktree` 回收本任务已并入且干净的工作副本；工具核对回收实体后再清掉该副本的 Git 登记，不用 `git worktree remove` 直接删除。别的任务留下、目录已经不在的工作副本登记，工具顺带一起清掉：只删登记，分支和提交都还在；盘没接上，或脱离分支的提交清了就找不到时，工具拒绝，这时把提交挂到一个分支上再清，盘没接上就留着。只读查看和测试不需要单独的工作副本。
- **单点动作前加一把短锁。** 安装或升级软件、发布规则、改计划任务这类会互相影响的动作，动手前用 `E:\.agents\tools\Invoke-ShortLock.ps1` 领锁，做完马上释放。同一种动作共用一个清楚、固定的锁名，持有人写当前宿主和真实任务号。先用 `-Mode Inspect -Name <锁名> -Json` 看现状，再用 `-Mode Acquire -Name <锁名> -Holder <当前任务> -Minutes 30 -Reason <一句话> -Json` 领锁；成功后才开始单点动作。别人的有效锁还在时，等它结束或先核对情况，不抢锁。需要续期时，同一持有人再次 Acquire；结束时在 `finally` 中用 `-Mode Release -Name <锁名> -Holder <同一持有人> -Json` 释放。短锁只避免并发相撞，不授予本人没有给的权限。
- **不动别人的东西。** 保留其他任务的改动和没提交的内容，不用 `git add .`，不从标题、目录或历史推断某处归自己。
- **停下时留好接续状态。** 没做完就停时，写清在哪个工作副本或分支、做到哪、还差什么，让后来的任务能接着做。
