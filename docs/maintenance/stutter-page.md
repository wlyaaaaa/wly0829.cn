# 驾驶舱的「电脑卡不卡」子页

唯一入口是 `/cockpit/stutter/`，由驾驶舱「电脑资源」一行的「卡不卡 → 详情」进入；没有独立顶层导航。页面展示当前资源状态、开机时长、已有资源走势、源能证明的原因分类、AI 执行回执与每周基座治理时间。

本人原话（北京时间 2026-10-08）：23:40「如果一个駕駛艙确实不够看，可以在拆一个页面出来」；23:41「之前的长开机卡顿页，不知道你怎么设计的；你看着办」「如果用户觉得立刻要处理，要有提示词复制给AI」；23:46「顶层只有一个驾驶舱页就够」；23:47 要求单条、区块、整页三级复制。新增给人看的文字由当晚 Opus 写手 6 定稿；对应模板保存在 `scripts/stutter-page-copy.json`，程序只代入真实字段与时间。

展示只读现有电脑状态接口，不创建采集器、服务、计划任务或客户端历史存储。`SiteLiveRuntime.readStatus` 保持驾驶舱现有读取、超时与备用源合同。来源未知、过期或读取失败不能显示当前正常；资源正常也不能代替整机流畅。正常时保留「觉得卡？复制给 AI」。

`host.uptime_seconds` 按自身采样时间显示开机时长。`hardware.health.pc_health` 保留 `state/reason_code/trend_state/coverage_hours/metrics/changes_24h`；新增 `trend_points` 来自原有五分钟资源记录，最多当前开机标记最近25小时，包含 `t/boot/metrics`。横轴是 `(t-boot)/3600`；同标记相邻记录超过15分钟时断线，不把空段画成平滑连续。图下注明的起点取实际展示的第一个记录点；`recording_started_at_unix` 和源的 `began` 同义，仅用于25小时预热倒计时（连续判定曾重置时可能晚于旧记录点）。有效样本数折算的 `coverage_hours` 不代替这段经过时间。

主线默认「内存占用」，实际为 Windows 已承诺内存与同次上限的比例；可切换剩余物理内存、系统句柄、可换出和不可换出内核内存。现有公开接口尚未提供近一小时帧时间次数、最长时长、最近时刻及事件分类计数；页面不伪造「无卡顿」、红色卡顿点或未采到分类的「没发现」。图的资源变化本身不能确定驱动、应用、硬件或网络为根因。

AI 回执使用卡顿事项的 `execution_started_at/ai_action`；没有回执就按文案明确尚未专门处理。治理日期只取现有 `automation.items` 中 `task-13a8bfdc29129046cf054f41` 的新鲜 `next_run_at`，不按星期编排。

复制提示只包含本机接口地址、真实条目 id、页面公开的一句说明和采样时间，不包含 `ai_hint` 或日志正文。事项按 id 去重；整页清单来自驾驶舱当前红、黄与带 `ai_hint` 的未知事项，顺序是红、黄、未知。单条与区块针对本页卡顿事项；只有一条时区块按钮隐藏。无事项时整页按钮灰掉。源还没有 `ai_hint` 时使用 Opus 的缺字段退路提示；浏览器拒绝剪贴板时展开可手动复制的文本框。

## 生成和整合

只生成子页及其资源，不写驾驶舱主页：

```powershell
python scripts/prepare-stutter-page.py --release site-release --output <独立空预览目录>
```

最终大批在自己的候选 release 上调用同一命令并加 `--delta`，得到稀疏增量和更新后的 `release-manifest.json`；通过现有最终大批流程物化、验证、发布。原 release 不改。驾驶舱主页的入口一行由驾驶舱单维护，避免并行覆盖。PCConfig 的字段须先在生产服务生效后才会出现实际曲线；字段尚未发布时，子页仍能显示已有状态，并明确没有走势点。
