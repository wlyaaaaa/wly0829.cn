# System 首页 owner 验收说明 v2

本说明冻结 2026-08-30 至 2026-08-31 的 owner 反馈。它拥有验收要求，不拥有动态项目事实；事实仍回到活动 E97、原始项目、Skills、PCConfig 与 GitHub 总索引。

## 页面范围

- System 成为 `/` 首页，项目目录迁移到 `/projects/`。
- 之前已经定稿的全站升级全部保留：唯一上下文搜索、完整搜索结果、项目状态与快照边界、`速览 / 产品 / 技术`、模块导航、Skills 单行分类、页头层级、移动端搜索和图库交互。
- 项目、规则、Skills 的现有 UI 不得推倒重做；允许刷新活动 E release、修正快照、补足原始来源后的产品内容，并完成已讨论的共享交互升级。
- System 首页允许独立设计，但必须沿用网站白底、深绿、细分隔线、慢速平行发丝、真实页头和字体体系。

## 产品定义

- 产品名方向：`个人 AI 协作系统`。
- 主问题方向：`AI 如何协助我完成工作`。
- System 不是当前十个项目的合集。完整范围是通用 AI 与智能体能力、全部 GitHub 项目、现行规则、Skills、资料与领域入口、电脑现场、执行工具、验证和恢复。
- 通用 AI 与智能体能力是系统成立的必要外部生产力；必须正面说明理解、推理、研究、视觉/文档、工具/代码、浏览器和并行协作等能力。
- 公网保持厂商中立：不写具体模型名或 Harness 概念，不把通用能力冒充个人开发，也不能写成项目 + Skills + 规则凭空产生智能。
- 个人系统的独特价值，是把通用能力接到个人项目、规则、Skills、资料、电脑、长期状态、执行、验证和恢复，让工作长期可用。

## 内容必须来自原始来源

- 不得只读当前网站摘要后扩写。
- 当前十个精选项目必须读取原始仓库 AGENTS、README、产品、架构、恢复、验证、关键代码和测试。
- 五份规则使用活动 E97；Skills 使用 canonical `SKILL.md`、当前供应和公开指南。
- 每项内容都要说明：实际帮什么、阻止什么事故、普通人怎样说、内部怎样协作、最后得到什么、发现问题和无法运行时怎样。
- 内容量应足以让 owner 恢复完整工作图景；“多十倍”指真实模块、流程、失败与依赖，而不是重复营销句。
- “文书和材料制作”可以进入全站；首页说明合同、正式说明、申请、事件材料和提交包怎样完成材料摄入、事实/原件核对、文书生成、格式验收、状态分层和恢复，不公开私人正文和个人结果。公开正文不出现“包装”施工词。
- `CACB` 等缩写不能承担产品解释；首页先用人话说明，再保留准确项目名。
- 页面底部不使用“诚实范围”标题。真实性边界放入对应场景、系统和证据说明。

## 场景要求

- 默认场景不以“发布项目”为主，应描述 AI 协助完成一个真实需求：可能发生在既有项目中，包含调查、复现、研究、实现、验证、自然使用和必要交付。
- 真实工作场景从左到右按现实使用价值排列；新增“找资料和媒体”和“交付一份文档”，与其余八项共同形成十个完整场景，不能为了填满标签栏增加空洞示例。
- 找资料和媒体从模糊自然线索回到少量真实原件，明确实际覆盖与零匹配语义，不全盘扫描、不复制或移动原件。
- 微信场景不能缩成一段录音。应覆盖具名聊天、回复关系、语音、图片、文件和扫描附件，最后形成纪要、需求、行动项、引用和待确认项。
- 文档交付必须把混合附件分流、扫描版面、乱码原字节、可编辑源稿、PDF 生成和逐页视觉验收分开；能打开不等于可以交付。
- 电脑故障必须由通用 AI 推理、TimeAudit 历史、PCConfig 与系统现场共同排查，不能只靠一个本地项目或监控峰值。
- 重装恢复必须体现资产、备份、依赖、项目、运行时、端口、软件、任务、自启动、凭据、受保护数据、登录、自然重启和分层验收，不能写成一键复制。
- 健康场景名称使用“健康协作”等完整产品语义；输入可包含病历、检查、设备数据、医嘱/订单、录音和沟通，不能缩成单一“第二意见”。
- 跨设备场景必须明确连续性产品是个人维护成果；通用 AI 与运行环境只是底层生产力，不能把产品写成外部平台自带。
- AI 辅助学习和真实任务能力验证应有独立、完整的人话说明。

## 系统组成与画面

- 当前 PC 端 UI 已基本通过；保留编辑式布局、场景切换和案卷分镜，只做内容、尺度、一致性和交互缺陷的小幅优化。
- 浏览器 100% 必须达到此前 125% 的舒适度；不得使用 CSS `zoom` 或整体缩放。System 有效宽度约 1160–1200px，正文 16–18px，系统名 20px 以上。
- 首屏不再使用大号“系统 / 不用记工具名”作为主张。
- 黑色可变详情条位置和长度不自然；若不能形成稳定证据说明则改为白色或浅绿固定字段。
- 真实场景与系统组成是两个独立章节；不得用跨页高亮、深浅或“本次使用 / 本次未用”制造只有滚回上方才能理解的隐藏联动。
- 系统组成可以有很多卡片，卡片可视化本身有价值；每张卡必须承担一个独立长期职责。上图讲职责和入口，下方项目版图讲全部资产身份与归属，不为了少卡而合并不同 Owner、运行桥或能力入口。
- 系统组成卡统一沿用此前选中卡的 2px 绿色实线框和很浅的绿色底色；悬停和键盘聚焦只轻微加深。绿色表示现役职责，不表示与上方某个场景联动。
- 系统组成必须包含实际系统名称和真实职责，不使用意图、路由、执行、结果等抽象占位撑画面。
- 所有节点最终可以进入对应项目、规则、Skill 或稳定首页锚点，再用浏览器返回恢复场景和滚动位置。
- 未来几十个项目只增加数据、能力家族或安全聚合，不缩字、不重排主构图、不生成占位项目卡。

## 移动端

- 必须检查 768、390 和 320。
- 场景标签可以横向滚动，但必须在下方显示“左右滑动查看更多”和同步位置条，不能依赖用户猜测隐藏内容；正文和系统组成不得横向溢出。
- 搜索折叠为图标的移动页头中，主菜单在姓名与右侧两个按钮之间等距居中，不继续贴着姓名排列。
- 案卷分镜按“用户原话 → 本次系统 → 输入 → 处理 → 结果 → 规则与边界”纵向排列。
- 系统组成移动端按泳道与职责卡纵向排列，不把桌面网格整体缩小，也不依赖桌面悬停语义。
- 项目、规则、Skills 原页面移动端不得回归。

## 内部验收与外部终审

- 在交给外部终审前，主任务必须先完成全站内容、架构、视觉、移动端、搜索、路由、无脚本、键盘、图库、控制台、构建体积和未来扩展的内部审计。
- 外部终审由 owner 使用 KIMI K3 + OpenCode 执行，范围是整个网站的内容与设计，不仅是 System 首页。
- 终审提示词允许 K3 自主发挥、推翻当前方案、反查原始内容并开启子代理；它不是橡皮章。
- 外部终审第一轮只读，给出事实证据、P0–P3、创意建议和最小修复方案；是否实施由 owner 与主任务决定。
- 终审范围包括 System、项目目录及十个项目、E97 规则工作台、28 个 Skills、搜索、路由、返回、404、SEO、无脚本、可访问性、100%/125% 和 1440/768/390/320。

## 交付条件

- owner 明确要求：彻底完成前不要把半成品交付给他验收。
- 内部全站验收完成后，提供 KIMI K3 + OpenCode 的自包含终审提示词。
- 处理外部建议并复审通过后，才进行最终 Git 收口、发布和公网回读。
