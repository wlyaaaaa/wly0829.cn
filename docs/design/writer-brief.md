# 网站写稿要求

网站 wly0829.cn 是本人（吴乐阳）自己每天用的总看板，也公开。读者首先是本人：他不懂技术细节，要的是一眼看懂、说人话、不猜谜。例行更新只把**变了的地方**写进已有内容，事实以当前来源为准。

## 先读

- [内容契约](panel-content-contract.md)，必读全文。
- 要改的页：本次任务指定工作树的 `sources/pages/<页id>/page.json`（文字作者源）和同目录 `layout.json`（构图，块用段首原话 `text_ref` 认文字）。写稿人只读，不直接改。
- 改数单已经把数字和日期填好时，以工作树里的当前文字为底稿，别用旧数字覆盖。主持按变化屏备齐旧文、新事实及来源、屏 ID、版面引用段首与占位边界；没有变动的屏不交写稿。

## 写法

- **说人话。** 陌生人 30 秒能答出：这页干什么用、能让它办什么、系统会做什么、拿到什么、什么时候停下来问本人、现在还缺什么。Owner、Provider、schema、runtime、SHA 这类词不进读者层；要留的技术事实放技术层，不删。比喻、第一人称、口语都可以，但不能改事实、边界和证据等级。
- **合并，不追加。** 就地改旧句子。不加更新日志、不加“本次更新”、不加重复卡片。没变的句子一字不动。不用更短的稿子盖掉更完整的有效内容。
- **事实分清。** 已实现、已启用、确有运行记录分开讲；没核实的写“未核实”或保留原日期。不把设计写成已上线。不用“刚刚”“最近”“昨天”，写绝对日期（北京时间）。
- **边界。** 不写密码、密钥、验证码。个人资料的公开分级按活动规则《个人资料与数据处理》的“公开个人数据分级表”，不自己收紧也不放宽。不暴露 curated_packaging、manual_owner_only、“包装内容”这类内部标签。不提任务号、派单、子代理跑了什么这种施工过程。
- **一处讲透。** 相同内容只讲一次，别处用〔链接〕指过去。链接写法：正文里写 〔显示文字〕，同屏 `links` 里配 `{"text":"显示文字","href":"/路径/"}`；新增链接在附件单列，施工的人会补。
- **占位别碰。** 正文里的 `{{...}}` 是构建时算的，原样保留。
- **功能变化一起核对。** 用法、例子、结果、边界、搜索摘录和演进要讲同一件当前事实，不能只改数字卡。

## 状态行（status_line）

首屏“现在”条是读者最先看到的。`state`、`last`、`facts` 写人话；`source` 改成不超过 16 个字的来源名（如“AI 使用记录”“项目仓库和运行记录”），不写“本轮”“按某版规则核对”“沿用既有说明”这种过程记录，也不写 Unknown。真正影响判断的缺口（没验收、读不到、有失败）放进 `facts` 或首屏正文，用一句人话说清，不能因为不好看就删。`facts` 里的数字以工作树当前值为准。

## 交稿格式（UTF-8，给机器合稿，别改格式）

每页一个文件 `<本次任务目录>/写稿/<页id>.md`，只列要改的屏；没有要改的页不要建文件：

```text
# <页id>

## 屏：<屏id>
<这一屏完整的 text，包括原有 Markdown 标题，一字不漏>

## status_line
{"state": "在用", ...}   （只在状态行要改时写；只写要改的字段）
```

`## old_urls` 下可放 JSON 字符串数组，与已有路由去重合并。JSON 可用 `json` 代码块包裹，未改的段落省略。

- `写稿/` 目录里只放页稿。附件都放稿目录外的 `写稿附件/`，文件名带组名；程序会把稿目录里的每个 `.md` 都当稿子读，放别的会让整批合稿失败。
- 屏 id、页 id 必须是现有的。要加新屏、新页，单独写到 `写稿附件/_新增-<组名>.md`，写清放哪、版面怎么排（照同页已有的屏）、完整文字、链接。
- 改了块开头那句话时，核对 `layout.json` 里引用它的 `text_ref`，把要同步改的列到 `写稿附件/_构图同步-<组名>.md`（页 id、屏 id、旧段首、新段首）。
- 新增的数字、日期要逐项列到 `写稿附件/_新增数字-<组名>.md`（页 id、屏 id、原文片段、来源、观察时间），施工的人要登记。
- 新增或改动过的标题要同步所属屏的目录锚点，列到 `写稿附件/_构图同步-<组名>.md`。
- 新增链接列到 `写稿附件/_新增链接-<组名>.md`。
- 写带时间快照的首屏句子时，列到 `写稿附件/_发布前重读.md`，注明来源和重读方法，构建前再核数字、时间和失败状态。
- 正文某屏里如果有一行恰好写成 `## 屏：` 或 `## status_line`，程序会把它当分段，换个写法。

## 交回

写进 `写稿附件/_回执-<组名>.md`，几行说清：

1. 改了哪些页哪些屏，每屏一句话说用途或状态哪里变了。
2. 核对过但没改的页（`已核对未变`）列页 id，主持要登记语义复核；每页一句依据（读了哪个来源）。
3. 拿不准、来源对不上的事实单列，不要猜。需要本人定的事单列。

## 项目组、技能组怎么做

- 材料是本次任务 `facts/` 里本组的事实文件：事实组从项目来源核对后写的，每条带来源和观察时间。拿不准或和看到的对不上，就打开它引用的来源自己核对；还对不上就列进回执，不猜。
- 页面多时按事实文件点名的屏读，不用把每页读完；但本组每页的 `status_line` 都看一眼。
- 事实文件里的“新增”“改变”“退役替换”都要落到屏上。它只是材料，怎么说由写稿人定：让本人一眼看懂这东西现在能干什么、现在什么状态、有没有事要他做。
- 首屏最重要：读者先看到的那一屏如果还在讲旧事，或者读完不知道这页干什么用，就改。
- `status_line` 的 `state`、`last`、`facts` 有技术噪音、过程记录或和正文打架的要改；`source` 超过 16 字的改成短来源名。只改 `status_line` 的页也要交稿。
- 事实文件写“未核实”“Unknown”“只读未运行”的，不要写成已验证。
- `skill-*` 页只归技能组；项目组发现技能页和项目事实冲突，写进回执。不碰别组的页。属于别的项目的事实，只在自己的页里放一句并用链接指过去。
- 还没上线的不写；正在施工的功能以线上现状和事实文件为准。
- 写完自查：屏 id 都存在；`{{...}}` 原样；读者层没有 Owner、Provider、schema、runtime、SHA；没有“本轮”“本次更新”；没有任务号和施工过程。
- 临时文件放 `写稿附件/tmp-<组名>/`，用完自己删；别碰别的目录，也别用通配符删东西。
- 需要本人资料时交回主持，不自己验证。
- 给主持的最后回复三五行、简体中文：改了几页几屏、最值得注意的变化、需要本人定的事（没有就写没有）。详情都在回执里。
