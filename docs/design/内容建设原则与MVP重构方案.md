# 看板内容建设原则

## 1. 第一读者是本人

网站首先要让吴乐阳自己看懂项目，而不是让外部访问者觉得“高级”。

外部表达不能压缩掉本人需要的架构、流程、边界、失败、来源和验证。页面漂亮、术语准确、测试通过，都不能代替用户能理解和使用。

## 2. 默认是真实看板

项目注册表里的默认模式是 `real_dashboard（真实看板）`：

- 写真实做成的内容；
- 写当前状态；
- 写没有做成或没有验证的部分；
- 写技术和产品设计；
- 写真实路径、ID、generation、hash 和验证；
- 不因为仓库公开而恶意保守。

只有用户明确指定的项目可以标记为 `curated_packaging（策展包装）`。包装项目也不能公开密码、密钥、token 或伪造可验证事实。

## 3. 唯一私有文档

`docs/design/private-content-rules.md` 是唯一不进入 GitHub 的项目文档。它负责包装项目和明确屏蔽内容的私有规则。

下列内容必须进入 Git：

- 产品规格；
- 内容原则；
- 项目注册表；
- 刷新机制；
- 当前 QA 报告；
- 构建、测试和发布入口。

可重建的 QA 截图留在 ignored 目录，避免二进制历史膨胀；这不等于把产品文档私有化。

## 4. 不写谜语

每个项目必须回答：

1. 它为什么存在；
2. 它实际包含什么；
3. 各组件怎样协作；
4. 用户怎样使用；
5. 哪些事不由它负责；
6. 出错时发生什么；
7. 怎样恢复；
8. 当前证据是什么；
9. 哪些结论仍可能被推翻。

对已经纳入看板的项目，公开页默认保留完整技术与产品细节。只排除私人敏感 payload（正文）
和密钥、令牌、恢复码等可复用秘密；模型、Provider、Profile、版本、模式、路径、端口、组件、
数据流、提交、hash、候选、安装/运行状态、失败、测试、E2E 和已知缺口都不因“公开”“太技术”
或版面长度而删除。涉及私人内容时只隐藏 payload/value，仍展示公开安全的身份、状态、边界和
它对当前判断的影响。

项目第一屏还必须直接显示 4–6 个会改变本人判断的当前选择。不同项目字段不同：模型项目写
当前默认模型、证据模型和云路线；机器项目写当前恢复版本、任务可见性和未安装阶段；Git 项目
写仓库数量、公开性、clone 覆盖和脏工作树；规则项目写当前权威来源、代际、能力供应与委派
状态。不能让读者读完整篇才拼出系统当前到底选了什么。

每份规则必须逐条展开。摘要只能作为第一层阅读，不能替代完整语义。

每个项目、模块、规则和 Skill 都必须先回答五件事：它替我做什么、为什么需要、一个真实例子、最后得到什么、通过/发现问题/入口不可用时分别怎样处理。然后再说明触发、输入、输出、流程、依赖、边界、失败、恢复和验证证据。只写“检查仓库”“处理文件”之类动作名称仍然属于谜语，因为本人还不知道检查结果会让系统继续、改道还是停止。

## 5. 英文术语后写中文

技术术语可以保留英文，但首次出现要写中文解释，例如：

- `Canonical source（规范源码）`；
- `Current E release（当前 E 规则版本）`；
- `Execution Owner（施工责任）`；
- `Read-back（正式回读）`；
- `Fresh task（全新任务验证）`；
- `E2E（端到端验证）`。

术语表解决“词是什么意思”，逐条正文仍要解决“在这个项目里具体怎样工作”。不能把术语表当完整说明。

自动术语标注只能作安全网：必须按最长短语一次替换，不能再处理自己刚插入的中文，避免 `Current task` 被拆开或 `Git 工作树` 出现套娃。`token`、`source`、`candidate`、`projection`、`limit`、`profile`、`Owner`、`Provider`、`Authority`、`root` 等会随场景变义的词必须由内容本身消歧，不能交给一条全局词典硬译。

## 6. 区分三种内容

### Active fact（活动事实）

来自现场 Owner，可能随时间变化，例如 current E release、dirty source、测试、服务状态、仓库提交和 Pages deployment。必须带观察时间和来源。

### Design principle（设计原则）

来自现行规则或项目设计，例如“项目规则拥有业务语义”“source 不等于 install”。不会因为一次服务离线改变。

### Example（解释示例）

帮助用户理解原则，不产生新规则。页面必须明确示例的地位。

## 7. 证据不互相冒充

- Source（源码）只证明当前写了什么；
- Test（测试）只证明指定回归；
- Install（安装）只证明落地；
- Publish（发布）只证明进入目标；
- Fresh task（全新任务）只证明新任务可发现；
- E2E（端到端）只证明一条真实路径；
- User acceptance（用户验收）证明当前问题真的解决。

缺失证据显示 `Unknown（未验证）`，不能自动填成 PASS。

## 8. 信息密度

压缩：

- 空白；
- 重复标题；
- 营销式 Hero；
- 为分类重复建设的详情页、多层 Tab 和内容副本；单行浏览筛选不在此列；
- 装饰性 CTA；
- 重复页脚。

保留：

- 完整事实；
- 逐条规则；
- 真实组件；
- 失败与恢复；
- 术语解释；
- 验证矩阵；
- 当前限制。

项目模块数量较少时直接显示所有入口，不使用下拉框。入口能在可读宽度内放下时单行排列；数量增加后按固定最大列数分行，每一行重新等分，不能出现残缺分隔线或为了单行缩小文字。

一屏可以看到多项真实内容，但不能通过缩小到不可读、强行截断详情或隐藏状态提高密度。

## 9. 项目和 Skills 顺序

- 项目顺序来自 `config/panel-projects.json`；`.agents` 永远第一。
- Skills 不建设分类详情页或分类内容副本；目录仍按实际价值排序，并可用一条单行用途栏做纯浏览筛选。
- “供应清单数量”和“公开面板收录数量”分别从当前快照与内容目录读取；本文不硬编码数量，筛选结果也不能冒充完整供应面。
- 价值综合使用频率、不可替代性、成熟度、真实 E2E 和失败成本。
- 排序变化是看板事实变化，但只有会明显改变用户查找和判断时才单独触发刷新任务。

## 10. 有阈值的事件刷新

Changed path 命中只表示“可能影响”，不自动创建网站任务。

真正创建全新网站任务的条件是：不更新会让页面上的事实、解释、边界、成熟度或用户决策实质错误。

不单独触发：

- 格式、注释和内部重构；
- 时间戳或 hash-only 变化；
- 被当前页面准确说明的 dirty/unreleased source 或 blocked project candidate；
- 不影响项目清单的测试；
- 小到可以随下一次实质更新一起维护的变化。

触发后使用一个新的独立网站任务，只处理一个刷新目标，不复用旧任务。Source 项目发布先完成，网站刷新不能进入 Source 的事务或回滚链。

## 11. 事实诚实

- PRIVATE 仓库不写成开源；
- Dirty/unreleased source 不写成 current E release；
- Source/install 不写成 E2E；
- 旧报告不写成当前状态；
- 错误测试环境不写成产品回归；
- 运行时离线不写成永久不可用；
- 失败修复后要撤回旧失败结论；
- 用户说看不懂时，继续补全内容，而不是解释为什么当前摘要已经够了。
