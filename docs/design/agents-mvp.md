# `.agents` 公开知识站 MVP 设计说明

## 1. 产品目标

这个站点不是个人履历，也不是仓库文件浏览器。它只解释一个项目：`.agents`。

长期使用时，读者应当先理解每个模块解决什么问题，再逐层看到它具体做什么、为什么这样设计、边界在哪里。技术细节用于帮助理解和复用，不用协议字段、运行状态或流程回执替代结论。

MVP 的成功标准：

- 首页只提供一个清晰、适中的 `.agents` 入口，不制造其他项目。
- 项目总览把现行内容自然组织为六个模块，并为每个模块提供真实详情路由。
- 想法页收录可以独立阅读、也能回到项目证据的公开设计原则。
- Skills 作为独立目录存在；它们不是项目，也不与 `.agents` 建立强制归属关系。
- 所有可见导航、链接与详情页在桌面和手机上都可用；站点只读，不出现无效操作。

## 2. 信息边界

### 展示

- `.agents` 的模块、规则与合同职责、公开安全的源码入口、工具职责、测试方式和模块关系。
- 现行 Personal Skill 供应清单中已安装条目的名称与公开安全描述。
- 能帮助读者理解设计取舍的公开想法。

### 不展示

- 密钥、Token、密码和任何可直接使用的凭据。
- 私人聊天、健康材料、诉讼证据等个人原始内容。
- 完整活动代际标识、动态 hash、ledger、nonce 或现场运行回执；这些内容会快速失效，也没有稳定阅读价值。
- 其他项目、Codex Remote、GitHub 总索引、PCConfig 或未来占位项目。

`.agents` 仓库保持私有。站点只提供带锁说明和 `https://github.com/wlyaaaaa/.agents` 链接，并明确说明未登录或无权限的访客可能看到 404。

## 3. 路由与内容结构

### `/`

一级项目页。顶部导航为“项目 / Skills / 想法”，右侧为 GitHub、哔哩哔哩、X 和邮箱。主体只有一个 `.agents` 入口，包含三至四行介绍、六模块预告、三条相关想法和“进入项目”。页面底部不重复宣传 Skills 或想法。

### `/projects/agents`

项目总览。说明项目解决的问题、整体工作方式、六个模块及其关系、仓库公开边界和阅读路径。

### `/projects/agents/:module`

六个真实模块：

1. `rules-contracts`：规则与合同内核。
2. `capability-routing`：能力路由与原生代理门禁。
3. `authorization-owner`：授权与执行 Owner。
4. `protected-policy`：受保护策略生命周期。
5. `skills-plugins`：Personal Skills / Plugins 供应。
6. `context-evidence`：上下文、健康与完成证据。

项目页使用稳定的左侧模块导航、单一正文列和右侧相关想法。当前模块完整展开，其他模块只保留导航；手机端改为可横向阅读的模块导航，不隐藏任何路由。

每个模块正文固定回答七件事：解决什么、具体做什么、为什么这样设计、边界在哪里、关键入口、如何验证、与其他模块的关系。标题结构稳定，但不使用状态字段堆砌。

### `/ideas` 与 `/ideas/:slug`

至少包含七条公开想法：

- 结果优先于过程。
- 验证要能推翻结论。
- 上下文价值在注意力，不在体积。
- AI 承担专业判断，但服从目标和硬边界。
- 长任务应可重建。
- 保护产品语义，而非文件形态。
- 只为真实变化设计。

目录页提供摘要；详情页采用“定义 / 解决的问题 / 实际用途 / 设计依据 / 边界”结构，并提供返回 `.agents` 项目的入口。

### `/skills` 与 `/skills/:slug`

Skills 是独立 Codex Skills 目录。数据依据 `personal-skill-supply.json` 中 `install: true` 的条目，以及对应 `SKILL.md` front matter 的公开安全描述；再按本站边界排除 Codex Local Remote，并把机器事实 owner 改写成普通读者可理解的用途说明。目录不提供分类器、筛选器、等级、日期或数量 KPI；每一项有真实详情路由，详情页说明用途、触发方式、为什么单独存在和边界。

## 4. 视觉系统

视觉真相来自两张选定参考图：一级页和二级文档页。实现保留它们的层级、留白、细边框、三栏文档结构和轻量绿色强调，同时执行以下修正：

- 主体使用白、黑和中性灰；绿色只用于当前导航、关键链接、细线和小面积提示，控制在约 10–15%。
- 不使用渐变、装饰插画、假预览图、项目图片占位或大面积彩色卡片。
- 标题使用高对比无衬线字体；正文优先系统中文字体，保证 Windows 和移动端可读。
- 卡片采用小圆角或近直角、1px 中性边框、无浮夸阴影。
- 图标统一使用 Phosphor 图标库；不使用手绘 SVG、emoji 或文本符号替代。

桌面内容最大宽度约 1360px。一级页项目卡宽度适中，不为单项目拉满屏幕。二级页在 1180px 以上使用“模块导航 / 正文 / 相关想法”三栏；平板降为两栏；手机为单列正文和可横向浏览的模块导航。

完整项目目录的未来布局要能在桌面首屏容纳至少四个真实项目、手机首屏至少两个真实项目；MVP 只有一个项目，因此只保留可扩展的卡片尺寸，不添加占位卡。

## 5. 交互与可访问性

- 站内导航使用真实 URL，并支持浏览器前进、后退和直接打开。
- GitHub、哔哩哔哩和 X 在新窗口打开；邮箱使用普通 `mailto:` 导航。
- 姓名链接回首页；无 About 页。
- 所有交互有明确 hover、active、focus-visible 状态；键盘可访问。
- 手机导航提供明确菜单按钮，展开后每个目标都可点击，页面切换后自动关闭。
- 尊重 `prefers-reduced-motion`；正文不依赖动画才能理解。
- 未知路由使用一致的 404 页面，并提供回首页和查看项目的真实链接。

## 6. 实现方案

- 保留现有 React + Vite 架构和 GitHub Pages 发布链，不使用 Sites、Vinext 或 DNS 变更。
- 使用轻量客户端路由，根据 `location.pathname` 渲染页面；枚举的站内路由在构建后生成对应目录 `index.html`，保证 GitHub Pages 直接访问返回真实页面。
- 内容集中在 `app/site-content.js`，页面组件负责语义结构，CSS 只负责布局和视觉，不在组件中复制长文案。
- SEO 元数据由路由在运行时更新；构建产物同时生成完整 sitemap。站点无登录、编辑、上传、删除、设置或服务端数据。

## 7. 验收与发布

本地必须完成：

- `npm run build` 与必要的路由/内容自动测试。
- 1440px、768px 和手机视口的浏览器截图与交互验收。
- 键盘、站内链接、外链、直接路由、404、SEO、无横向溢出和 console 检查。
- 两张视觉真相与同视口实现截图的组合比较；所有 P0/P1/P2 修复后，根目录 `design-qa.md` 写明 `final result: passed`。

发布保持 GitHub Pages：定向提交、normal push `main`，等待 Actions Pages 完成，再从根域公开回读。最终证据需要本地 HEAD、远端 `main` 和部署 commit 一致；只有这些同时成立才释放 whole-project Owner。
