# 按需更新操作清单

本人说“更新一下网页”“全部更新一下”，或点名更新一个项目时，按这份清单把来源里的新事实合进已有页面，验收后发布。最终交付是能在公网读到的正确页面、明确的未解决项和真实用时；取数单、构建成功或资源上传均不能单独证明完成。网站仍由本人发起更新，不新增定时刷新、监听程序或后台服务。

以下入口已在 `main` 使用；每轮核对当前输入与实际回执，不把工具可运行当作本次内容或发布已通过。日常维护入口见 [网站维护](maintenance.md)，完整发布协议见 [发布与扫描](publish-and-scan.md)，作者输入、缓存和构建回执见 [Astro 说明](../site-astro/README.md)。

## 日常路径的分工与预计耗时

日常指本人点名或涉及的项目不超过 5 个、全站带日期数据按清单批量重取、涉及的冻结页不超过 10 页、没有新项目或新技能页。允许规则换版，整站重建在第 3 步提交后的后台构建里完成，不占事实和写稿主线；同一 `dist` 单写入者，后台构建期间不改源，第 6 步合稿要等它结束（2026-10-12 第 2 次计时演练把规则换版重建压在第 6 步，构建 412 秒、第 6 步 19 分钟，据此改）。前提是本轮所需来源绑定完整，常驻缓存可复用。

从本人提出到公网回读通过不超过 **90 分钟**；只有数据变化、用途和边界没变时目标 **60 分钟**。“全部更新”或新增项目仍按不超过四小时处理。超过 90 分钟就是流程缺陷，要据本次回执指出卡点并登记修正项；下面的预算不能充当完成记录。

### 清单维护是日常流程的一部分

常设清单仍是 `sources/refresh/registry.json`，入口白名单是 `sources/refresh/entries.json`。写某页或某项目事实的 GPT，在改页面的同一个提交里登记全部带日期和数字的展示项；新技能页、新项目页也必须在同一提交里登记。Opus 写稿新增数字时逐项列出来，由 GPT 补登记；不能把新增登记留到下次更新。

每条来源必须定位当前页面的实际字段或唯一捕获范围。同页另一数字已经登记、旧 `page_number` 还在、入口能返回数据，都不能替代当前展示位置的绑定。`status_line.state` 是人工判断，历史项保留当时事实；其余展示项须有生效自动记录，或五种合规 `manual_reason` 之一及具体 `manual_route`。五种理由是 `needs_admin_rescan`、`ui_only`、`external_account`、`judgment`、`source_broken`；来源损坏时取法还要说明修复去向。

截至日期使用 `qualifies` 明确指向它注明的数据记录，不另造一份日期来源。程序的同屏邻近数字建议由 GPT 核对后写入；建议本身不算登记。新截至日期取这些记录里最早的观察日期，有一项 Unknown 就保留原日期。只读入口登记前核实不写东西，私人库只取计数和状态，不把条目原文输出给模型。

改数绑定优先登记实际 `field` 与唯一、含具体含义的 `page_pattern`，完整捕获数字；已迁移的记录删除旧 `start/end`，避免改稿后字符偏移漂移。裸数字正则、旧值片段、失配或非唯一捕获仍拦下。数字与日期可跨字段通过 `qualifies` 配对，由日期记录独占截至编辑；共享同一日期的数字一起通过，独立配对不因同页其他失败项连坐，字段哈希在筛掉失败组后重算。覆盖末日不提供时分，不能拿取数时刻补成新的验证时间。

项目计数必须读取当前 enabled Registry 并排除 `parent` 模块；`project_scope=active_projects` 只接受 `kinds=["project"]`，不含冻结页。明确写“含冻结”的既有总量采用独立的 `registered_projects_including_frozen` 口径，不用在用项目数替换它。配置不可读时返回 Unknown，不回退到遍历页面凑数。来源为 `source_precision=estimated`、展示要求 `display_precision=exact` 的项保持待核，估算值不能覆盖精确值。

`--strict` 是必须通过的门。分路施工先运行 `refresh.py --inventory --strict --only <页id,...>` 修自己的页，合入前再跑全站严格盘点和 `tests.test_refresh_registry_complete`。漏登记会列页、屏及原文片段并非零退出；全站漏登记须为零，当前非历史、非 state 展示项自动覆盖至少 85%，人工项不超过 15%。局部 `--only` 通过不能证明全站通过。

## 0 准备常驻工作树

常驻构建工作树固定为 `E:\Cache\wly-site-build\wt`，由主持负责准备和维护。不要每轮另建临时构建工作树。每轮切换前先确认未提交源码改动已经归位、没有别的任务写同一 `dist`；不清楚归属时交回主持，不重置或清空来求“干净”。

```powershell
Set-Location -LiteralPath 'E:\Cache\wly-site-build\wt'
git status --short
# 确认未提交源码改动已妥善处理；记录切换前 package-lock.json 指纹。
git fetch origin
$refreshStamp = [TimeZoneInfo]::ConvertTimeBySystemTimeZoneId([DateTimeOffset]::UtcNow, 'China Standard Time').ToString('yyyyMMdd-HHmmss')
git switch -C "refresh/$refreshStamp" origin/main
```

前一步失败就不执行下一步。第一次安装运行 `npm ci --prefix site-astro`；后续只有 `site-astro/package-lock.json` 内容变化时重装。保留根及 `site-astro` 下的 `node_modules`、`site-astro/.cache`、`site-astro/public`、`site-astro/src/content/rendered`、`.publish/typeset-out/_cache`、`dist`。同一输出目录单写入者的完整说明只保留在 [Astro 说明](../site-astro/README.md#唯一构建入口与回执)。

用 `git rev-parse --path-format=absolute --git-common-dir` 找共享 Git 目录，核对其中 `wly-oss/published.json`。它是完整部署和公网回读通过后写下的成功记录，不是最近一次构建。记录缺失时先报告无法证明成功前版并核实真实成功部署；构建的 P0-1 回退可以使用旧 `dist` 清单并提示地址可能换新，但不能把该回退当作发布成功证据。

活动 E 规则换版时，先运行 `python scripts/prepare-astro-release.py refresh --output <规则审计JSON>` 更新版本化规则源，核验后安排全量构建。构建不会自动把本机规则变更写进网页。

## 1 取数并生成日期清单

从仓库根运行：

```powershell
# 只盘点，不自动重取事实；写给 AI 接续用的两份清单。
python -B -X utf8 scripts/content-refresh/refresh.py --inventory --strict --output <本次任务目录/盘点>
# 日常：全站带日期数据按清单批量重取，总取数时限 300 秒。
python -B -X utf8 scripts/content-refresh/refresh.py --strict --output <本次任务目录/取数> --total-seconds 300
# 分路补登记：只检查本路页面；不替代全站严格检查。
python -B -X utf8 scripts/content-refresh/refresh.py --inventory --strict --only <页id,...> --output <本次任务目录/本路盘点>
# 这条命令只生成项目计划，不限制上面 refresh.py 的取数范围。
npm run refresh:ai -- --project <Registry中的项目id>
```

默认 `refresh.py --output` 会遍历完整来源表；`refresh:ai -- --project` 只生成计划，不会替它筛选来源。日常也批量重取全站已登记的当前日期事实，语义调查和写稿仍只覆盖点名项目及实际受影响页。`--only` 用于分路登记和局部诊断，`--registry` 可读取保持原结构的独立来源表；这两种局部结果均不能冒充全站清单验收。没有已登记记录的展示项会使 `--strict` 失败，先补真实来源或合规人工取法，不伪造记录通过校验。

`dated-inventory.json` 逐项列原文、原日期、所在页与屏、来源记录和能否自动重取；`fact-tasks.md` 按来源项目分组，交给事实调查代理。清单的 `surface` 分为 `visible`（页面展示）、`author`（构图等作者输入）、`reference`（登记及内部说明）。原始“截至”匹配保留在覆盖统计中；不能把 scene、portrait 或内部备注里的命中全算作可见事实，也不能拿总匹配数代替展示项完整性。只将需要更新的可见事实交事实任务，未绑定来源的项标“待登记·人工取数”。

全站清单用于发现遗漏，不扩大本次授权范围。点名更新的语义调查只覆盖该项目及直接受影响的 Rules、Skills、System；“全部更新”按 Registry 选择可更新项目，冻结项目与需明确点名的页面仍遵守各自边界。私人来源只有登记核实的 `entry`、`sqlite_ro`、`log_window`、`usage_ledger` 四种只读办法可由程序取聚合值；旧私人办法仍交领域事实代理，不能把可自动重取的入口长期留作人工摸索，也不能把条目原文输出给模型。

入口 `argv` 为数组、不经过 shell，只运行 `entries.json` 中核实为只读的配置；SQLite 使用 `mode=ro` 且只允许单条 `select`。日志按登记匹配和时间窗读取，使用记录共用一份登记账本。默认总取数 300 秒、至少 8 路按来源并行，同一个 `entry` 一轮只运行一次供多条记录复用。时限耗尽的项交回 Unknown，不延长时限来凑齐结果。

`usage_ledger` 的七日用量取两路账本共同完成水位之前的 **7 个完整日**，按北京时间日界计数，不含正在进行的一天；截至日期为共同完成水位的前一天。两路水位必须存在、带时区并已完成初始化，不要求水位晚于当前时刻。取数观察时间和账本覆盖末日分别保存，配对的 `qualifies` 日期采用覆盖末日；水位不可用时数字及其截至仍为 Unknown。

## 2 定范围

主持收到每个项目的简短变化说明：新增了什么、哪项改变、哪项退役或替换、还有哪些 Unknown，以及影响哪些页面。Git 提交和路径只用于找候选；还要读取未提交候选、当前清单、配置和运行回执，不能用“提交没变”断言事实没变。

用 `site-astro/tools/frozen_inventory.py` 的盘点结果按项目路由找到相关冻结页。完整冻结清单原有 209 路由；本次 175 页迁移清单排除了冻结项目的 31 页和 Unknown 的 3 页。这些是一次性选择，后续数量以当轮盘点为准。日常更新仅将本次变化会使其明显过时的冻结页列入迁移；无关冻结页保留旧快照。

把原生页、冻结路由、日期事实、关联 Rules／Skills／System、未涉及页和不能读取的具体项写进本次 `scope.md`。范围经主持确认后再施工；后续新事实只在同一范围内归位。只改措辞的工作沿用已接受的语义，不借机重做全部内容。

## 3 分组调查事实

第 2 步事实组同时处理 `dated-inventory.json` 单列的 `review_stamps`：碰过的页更新核对戳，填本次事实核对日期；未涉及的页保留原戳。模块页的“项目事实核对截至”等整页核对戳不绑定取数来源，不计入 85% 自动覆盖分母，不能为它造无关提交数、配置数或 `judgment`。核对戳表示事实组本轮已核对该页，独立数字取不到仍保留原日期和 Unknown，历史证据仍保留当时日期；盘点程序读了页面文件不等于事实组已核对，程序不自动写今天。

按来源项目分组，每个涉及项目派一个 GPT，结合 `fact-tasks.md` 查 Git、未提交候选、运行回执和非 Git 状态，同时补自动取不到和人工项；任务单超过约 25 项可分组并行。每个事实代理派单都写明：**20 分钟内交回；单项超过 3 分钟取不到就标 Unknown、保留旧日期，接着做下一项；到点交回已取到的，其余同样标 Unknown。** 每项返回新值、统计口径、来源、观察时间，以及旧值是否被新证据推翻。带日期的展示数字、状态行、首屏数字卡、`source_note` 等必须逐项重取；功能变了而提交没变也要重取。

取不到的项保留原日期并明确 Unknown，指出缺少哪个来源或哪种观察，不拿旧数冒充新数。历史阶段数字保留当时口径；冻结页原快照中正在用作现状的数字，迁移后必须重新取。网站内容可按已确认例外读取所需私人来源；这项例外免除资料锁要求，不取消选定页面已经明确的数据范围。最终公开的值另按活动规则的唯一公开分级表和所属页面限制判断，不复制一张项目自设分级表。

来源坏了时按真实责任修复来源，页面只写已证实的结果和缺口。例如 AI 使用账本停写，先交拥有写入链的项目修复；修好并回读前，相关页面保留旧日期与 Unknown。不能为了赶这轮进度伪造新统计。

改数单跳过原因中，`old_value_not_whole_number` 表示旧值截断了完整数字，`scope_mismatch_or_unverified` 表示登记与正文口径不同或无法核实，`as_of_link_required` 表示找不到可安全联动的观察时间；这些项保留旧数和旧日期，交事实组核对，数字与观察时间的配对编辑须一起成功才应用。

## 4 改内容与迁移冻结页

常规编辑在仓库根的 `sources/pages/<页id>/page.json` 中进行，构图在相邻 `layout.json`，配图在 `sources/assets/_library/asset-map.jsonl`。不直接把成品 HTML 当作者源；若已有直接编辑的 Markdown，先按 [Astro 说明](../site-astro/README.md#内容文件怎么写) 统一作者输入，再恢复转换。将变化合进现有解释，没变的内容保持原样，不加更新日志或重复卡片，不用更短、更旧的稿子覆盖更完整的有效内容。

GPT 先看取数生成的 `number-edits.json`：每项有页、字段、字符范围、旧值、新值、观察时间和记录 id；同口径数字和截至日期可机械填回原位。

```powershell
python -B -X utf8 scripts/content-refresh/apply_edits.py <本次任务目录/取数/number-edits.json>
# 只应用一个分路拥有的页面。
python -B -X utf8 scripts/content-refresh/apply_edits.py <改数单.json> --only <页id,...>
```

应用前核旧值仍在原位，不符就跳过并报告；重复运行不产生第二次差异。工具不写叙述，不判断产品含义是否改变。GPT 对照事实判断改数后是否还影响用途、能力、边界或状态，受影响的解释交 Opus 改写，纯数据变化不让 Opus 重新调查事实。

Opus 每页交一份 UTF-8 Markdown 稿，第一行是 `# <页id>`；只列本次需要改的段落。`## 屏：<屏id>` 下放该屏完整 `text`，包括原有 Markdown 标题；`## status_line` 下放 JSON 对象，仅合入列出的字段；`## old_urls` 下放 JSON 字符串数组，与已有路由去重合并。JSON 可用 `json` 代码块包裹，未改的段落省略。GPT 用 `apply_rewrites.py <稿目录>` 机械合稿，不再逐屏手工搬运。工具先校验整批稿、目标页、屏 id 和 JSON；任一不符，整批不写并非零退出。合稿保留未列字段与 LF/CRLF，重复运行不产生差异；`--root <仓库根>` 用于隔离验证。

功能变化时一起核对用法、例子、结果、边界、搜索摘录和演进，不能只改数字卡。标题改了同步修改所属屏的目录锚点；每个写稿组都在隔离副本试合稿并运行 `convert_page.py --check-all`，标题定位点与横排卡片失衡问题在交稿前修好。

### 冻结页使用同一个转换工具

路由清单是文本文件，每行一个完整路由，保留结尾斜杠。工具入口：

```powershell
# 先预演，检查报告中的文字保留、拆屏、丢弃片段与警告。
python -B -X utf8 site-astro/tools/frozen_to_pages.py --routes <路由清单文件> --report <转换报告目录> --dry-run
# 样板通过后实际生成作者输入。
python -B -X utf8 site-astro/tools/frozen_to_pages.py --routes <路由清单文件> --report <转换报告目录>
# 仅在确认已更新事实已保留、确需重转时使用 --force。
python -B -X utf8 site-astro/tools/frozen_to_pages.py --routes <路由清单文件> --report <转换报告目录> --force
```

工具只搬运文字、结构和链接，按固定图标表与构图模板生成 `page.json`、`layout.json`、素材表追加行及 `convert-report.json`，不判断新事实、不写产品叙述。已有作者页默认跳过；覆盖需明确 `--force`，覆盖前保存并核对已经更新的事实，随后人工并回。页 id 由项目和模块 slug 组成，原路由由新版认领。重名与其他结构异常应报错处理，不能自动另起一页来绕过。

第一次批量启用，先用这三页样板：

| 路由 | 样板验什么 |
|---|---|
| `/projects/localocr/input-routing/` | 短页的卡片、图标与空白 |
| `/projects/pcconfig/secrets-providers/` | 长技术页的拆屏、表格和长列表 |
| `/projects/agents/capability-routing/` | 大改页从搬结构到重写讲解的交接 |

独立 Claude 对照原冻结页与转换报告，核对规定保留文字不少于 97%、未规定丢弃的片段没有消失、警告已处理；再看 1920 与 375 宽截图及相关检查结果。三页都通过后固定 `frozen_module_icons.json`、`frozen_module_layout.json`，再批量施工。没通过就改共用模板或转换规则、重跑样板，不逐页手摆来掩盖规则问题。

批量按每批约 25 个路由依次运行 `npm run build -- --pages <路由1,路由2,...>`，每批完成后显式扫描同一批路由。排版浏览器最多两个，同一 `dist` 的各批构建不能并行。每批零失败才继续；失败修共性模板或转换规则，再重转该批。转换报告不得留未处理警告，最终搜索要能找到每个新页标题；手机五宽检查样板全做，批量每项目抽一页。

结构生成后，GPT 按项目重取并更新 `page.json` 的文字与 `status_line`；需要重新讲清产品的大改页交 Opus。事实代理不自行改 `layout.json`。结构阶段与事实阶段的交接要防止后续 `--force` 覆盖新事实。

保留 `sources/frozen-site` 原快照及其 manifest，不在迁移任务中删掉。新版原路由接管后，回退需撤销对应的新作者输入、素材表追加行和生成物，再重新构建，确认冻结路由恢复；不能把撤销作者页与重新部署旧成品混成一个动作。175 页全部验收后是否清理旧快照另开 P2，不在这次迁移中处理。

## 5 独立复核

Claude 收到本人要求的出处、`scope.md`、日期清单、各项取数证据、转换报告和实际 diff。日常预算 8 分钟、硬上限 12 分钟，简短复核范围是否漏页、日期是否重取或明确 Unknown、公开风险，并抽读 2 页。清单维护复核看全站严格检查是否通过，不由 Claude 重新逐项取数。抽读时仍需核对陌生读者能否从产品层说明用途、输入、过程、结果及停止条件，技术层是否保留事实、故障、恢复与证据。

新项目、全量刷新或完整性修复仍需从当前来源独立重建长期能力清单，再比较产品与技术两层，不能只按现有模块名打勾。一项影响用法的能力遗漏就是 P0 内容缺陷。复核只提出有来源的问题，修复后复查受影响范围；单测和扫描不能代替实际阅读。

## 6 校验、构建和扫描

使用已合入的校验、构建和扫描入口：

有稿时先跑 `apply_rewrites.py` 合稿，紧接着跑 `refresh.py --inventory --strict`，缺口当场补绑后才构建。

```powershell
# 有 Opus 稿时先机械合入；纯改数、没有稿目录时跳过这一条。
python -B -X utf8 scripts/content-refresh/apply_rewrites.py <本次任务目录/写稿>
python -B -X utf8 scripts/content-refresh/refresh.py --inventory --strict --output <本次任务目录/最终盘点>
python -B -X utf8 -m unittest discover -s tests -p "test_content_refresh_*.py"
python -B -X utf8 -m unittest tests.test_refresh_registry_complete
python -B -X utf8 site-astro/tools/convert_page.py --check-all
npm run build
python -B -X utf8 site-astro/tools/scan_glance.py --dist dist --pages published-diff --out <本次扫描目录>
```

严格盘点和完整性测试是构建前必须通过的门；新页漏登记会直接失败。工具验收另外实跑整表 `refresh.py --output <目录> --total-seconds 300`：取数不超过 300 秒，`result.json` 中自动项取到新值的比例至少 90%；`source_broken` 项单列，不计入这一比例。登记自动覆盖的 85% 与本次自动取到新值的 90% 是不同指标，不能相互代替。

`--check-all` 在构建前做图位、转换契约、同一横排卡片正文长度及标题定位点的纯文本预检，不写作者源；目标 60 秒内完成。预检只提前拦截文字和定位错误，最终几何与浏览器扫描仍须通过。构建回执核对 `seconds`、`rebuilt_pages`、来源版本及最终 `files`；增量 110—300 秒、全量约 583—830 秒都是裁定单给出的参考区间，必须用本次回执验证。常驻路径只是保留缓存，不能靠路径存在就宣称性能验收。

`published-diff` 比较上一成功发布与最终成品的 HTML 哈希，覆盖累积多轮构建后的真实变化，不能用最后一次 `rebuilt_pages` 替代。缺少成功前版时按工具提示核实范围；需要显式传路由或 `all` 时记录原因。日常与规则换版均以 `published-diff` 变化页扫描为发布门槛；只有外壳、排版引擎或共享脚本变化时另外做全站扫描。首页 `/` 保持锁定，所有扫描模式均排除首页。例外：“这套东西办过的事”这张图引用的项目数字或来源日期变化时，运行 `python -B -X utf8 scripts/prepare-home-highlights.py --output <本次任务专用临时目录>` 随更新重新生成；数字和日期都绑定所属项目登记。只允许该图和相应图片坐标、文字等价稿变化，首页其他部分保持原样。本次构建临时设置 `SITE_ALLOW_HOME_BYTES=1`，不保留为日常环境配置。

扫描检查大块空白、压叠、裁字、空图框、请求／站内链接与锚点错误、可见入口点不动。它等待稳定画面并截图，不验开场、动效或全过程加载体验；AI 可看静态截图，动效由本人验收。两种桌面视口的每页结论、计时和截图在 `scan-result.json`；手机检查按前面的样板与项目抽样执行。

扫描器只对指定偶发 transport（传输）错误自动重试一次，两次结果都保留；其他失败及重试后失败不能忽略。最终所选变化页必须零失败，且扫描前后成品文件表一致。

搜索索引的 gzip 体积超出 Registry 复核线时，构建只输出警告，并把实测值写入 `release-manifest.json` 的 `search_budget_review`。检查重复内容、依赖与加载代价后再决定处理，不删有效正文来凑预算，也不把超线当作发布失败。构建显示“连带变化”时查清资源与页面关系；首页字节守卫失败先查原因，不把 `SITE_ALLOW_HOME_BYTES=1` 留成日常绕过开关。

## 7 先上传资源，再正式发布

发布只使用刚通过扫描的同一份 `dist`。扫描完成后任何成品文件增删改都需重新扫描，不能沿用旧 `scan-result.json`。现有公开目标与正常更新授权沿用项目规则；明确叫停或范围外动作依其实际边界处理，不再新增一套审批流程。

```powershell
# 第一步：预演计划，不上传、不推送、不部署、不写成功指针。
python -B -X utf8 site-astro/tools/publish_site.py --dist dist --scan-result <scan-result.json绝对路径> --dry-run
# 第二步：资源上传和回读，仍不切换公开网页。
python -B -X utf8 site-astro/tools/publish_site.py --dist dist --scan-result <scan-result.json绝对路径> --upload-only
# 第三步：正式发布同一成品；已传且大小与 MD5 相符的对象通过续传检查复用。
python -B -X utf8 site-astro/tools/publish_site.py --dist dist --scan-result <scan-result.json绝对路径> --output <正式发布输出新目录>
# 正式发布已返回、发布锁已释放后，单独清理；可与下一轮取数并行。
python -B -X utf8 site-astro/tools/publish_site.py --retention-only <正式发布输出目录>
```

预演核上传计划中的变化 HTML 与扫描范围是否相符，`/search/` 等实际受影响页也计入。首页虽排除视觉扫描，发布器仍 GET 核关键页字节。变化数明显超出预期先查连带变化；预演传输时间按固定速率估算，不是网络实测，不包含 Pages 排队。

`--upload-only` 在 OSS 上传新增或变化资源，并以 HEAD 核大小与 MD5；回执 `status=uploaded_only`。它不推 `site-dist`、不触发 Pages、不写 `published.json`。正式发布先完成资源证明，再正常推送 `site-dist`，从 `main` 触发 `pages.yml` 并传成品 `sha`，按返回网址取得该次 run id、等待成功，再 GET 首页、驾驶舱、`/computer-access/` 和全部变化 HTML，核 HTTP 200 与 SHA256。超时或失败保留回执，不写成功。

资源、部署和公网回读全部通过后，发布器才更新 `<git-common-dir>/wly-oss/published.json`，以此作为下一轮增量基线。正式发布默认不清理旧对象：`publish-receipt.json` 写 `status=published`、`publication_status=published`、`oss_retention.status=deferred`，删除数为 0，命令成功退出 0。回执包含后续清理命令；`--skip-retention` 仍可兼容使用并记录 `skipped_by_request`。发布已上线与清理未运行是两件事。

发布命令结束并释放锁后，单独运行 `--retention-only <正式发布输出目录>`；可与下一轮调查、取数并行。它只接受成功实发回执，重新取得现有短锁，执行原有精确候选、版本、大小和 ETag 核对及删除回读，完成后释放自己取得的锁。候选查询已有 8 路并发；默认每轮最多核对 1000 个受管 key，可用 `--retention-max-keys` 调整。保留该正式发布输出目录直至清理结束；若后续成品已替换这次发布，旧回执不能用于清理，改用当前成功发布的输出目录。

清理的预演与结果独立写入 `oss-retention-plan.json`、`oss-retention.json`。清理命令返回 `retention_complete`、`retention_incomplete` 或 `retention_dry_run`；有残留时仅清理命令非零退出，不改已上线的发布结果。缺证明、多版本、未知对象和其他施工清单继续保留并说明；不按年龄撤销、不整桶普扫。可先给清理命令加 `--dry-run` 只看计划。预演、资源上传或发布失败都不触发对象退役，也不能凭正式发布退出 0 声称清理已完成。回退入口见 [网站维护](maintenance.md#成品部署与回退)，细节见 [发布与扫描](publish-and-scan.md)。

## 8 核对应关系后再宣称完成

源码 `main` 与成品 `site-dist` 是不同内容的分支，通常具有不同 SHA。不能要求“本地 HEAD、远端 main、Pages 三个 SHA 硬等”；要分别证明来源和上线结果：

| 要证明的事 | 使用的证据 |
|---|---|
| 本次源码已进入真实默认分支 | 本地已接受的源码提交与远端 `main` 回读相符；分支合并后记录实际 `main` SHA |
| 成品确实来自这份源码 | 构建回执／来源清单的 `source_commit`，及发布回执的 `source_commit`、`source_commit_evidence` 对应已接受源码；还要核对未提交输入，不能拿后来 HEAD 冒充当时输入 |
| 部署的是本次成品 | 发布回执 `site_dist.commit`／`commit` 与工作流输入 `sha` 相符，并核该次 Pages 运行；手动运行的工作流 HEAD 可能是 `main` SHA，本身不能证明成品身份 |
| 公网读到的是部署成品 | `release-identity.json`、资源清单、关键页及变化页 GET 字节与扫描后的成品对应，OSS 资源回读通过 |
| 成功基线已推进 | `published.json` 的成品提交、部署标识、manifest 和 readback 对应本次正式发布；上传或 dry-run 不满足 |
| OSS 退役已处理 | `oss-retention.json` 的精确候选、保留施工清单、删除后回读及实际删除量；任何 deferred、失败或预算残留均如实报告 |

若构建来源缺失，当前发布器允许写 `Unknown`，或通过 `--source-commit <40位SHA>` 提供明确来源；只有真实核过作者输入才可使用该参数，不是把当前 HEAD 补进空格。Unknown 可以如实交付为缺口，不能支撑“源码、成品、公网完整对应”的完成声明。

完成声明依赖本次来源绑定与展示位置验收、Claude 简短验收及真实端到端记录；相关内容还须通过来源完整性、实际阅读、构建、公开内容与变化页扫描门。工具可用不能代替来源覆盖、整表实取和演练结果。常驻工作树必须有实际构建回执，证明缓存复用和真实用时，不能仅凭这份文档通过。
