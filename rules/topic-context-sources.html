这里说清事实找谁、哪些项目冻结、项目分几档维护，以及长任务怎么接续。授权、施工和执行结果由各自专题负责。

事实找谁

  • E:\.agents：AI 的行为规则、授权、能力路由、规则发布、个人技能和插件、跨项目协作；推送前检查、私人配套库查询和 GitHub 删库、转移、改公开的执行入口在 project-entry-gate 技能里。
  • E:\PCConfig：机器路径、端口、自动任务、运行环境、数据源、迁移、备份和恢复事实；本机每个仓库在哪个文件夹、网站显示哪些项目、公开仓库配哪个私人配套库，也登记在它的 registries/ 里。
  • 具体项目：业务含义、领域数据、兼容、启动、测试、部署和生成区。

按需要一步步读：看到绝对路径不等于要把两个基座全扫一遍。普通项目先读目录链上的规则和本地状态；公开或私有、远端、分支、同步这类 Git 事实在仓库里用 git、gh 现查，推送、公开、删库这类动作前按 project-entry-gate 技能检查；只有机器事实会改变决定时才问 PCConfig，只有规则、能力或授权会改变决定时才读本仓库对应的专题。不知道的就说不知道，不从别的来源猜。

两个基座的日常治理是发现并修好有事实依据的问题，不是补跑备份。Windows 计划任务机制正常时，只看它有没有按时跑、回执对不对；不为了刷新成功时间或让报表变绿去额外运行备份。已经证实的机制缺陷在原项目里修好并做相应的局部验证；本人暂停的任务保持暂停。基座治理里说的“流量”指代理流量，阿里云的流量归网页治理（本人 2026-10-07 22:47 更正；视频语境里的“流量”另按视频理解）。

冻结的项目

冻结的项目（约法 L24）：本人没主动提这个项目的具体需求时，AI 不主动看代码、研究、审计、修复、升级或优化；它们的自动任务停用，换电脑时也不重建。本人说“全部项目”“全局完善”这类批量指令时，默认不包括冻结项目，也不先读它们的代码再决定。本人点名提具体需求时，只按这次需求取材和处理，不需要说“解冻”，也不因此恢复日常维护；只提到名字不算需求。活动项目引用了它、模型升级了或发现能优化，都不是去碰它的理由；真需要改冻结项目时，说清依赖和缺口，等本人提出。识别和排除冻结项目时，只读最小的身份和状态信息。

冻结名单只维护在这里。仓库标识都是 wlyaaaaa/<repo>，名字比对不分大小写。

冻结一个项目要说清真实理由：为什么不值得再单独维护（被什么替代了、依赖没了、AI 现查就能做到、单独维护反而添乱、实际没人用等），以及原来的用处现在由谁承担。“已存档”“内容已归位”“不再维护”只说了结果，不算理由；说不清就问本人。网站项目总页冻结卡上的“停下原因”照这个写，规矩在网站仓库 docs/design/panel-content-contract.md“退役内容的去处”。

长任务接续

开对话、压缩和恢复时不注入决定短表、要求表或以前的原话，只按下面递工程和《他要什么》的位置。AI 读的是全局规则和当前项目的规则。原生子代理跳过 SessionStart 时从派单和原任务状态接续，不额外读原话。不改全局窗口、不强制换对话。

短任务单写本人要的产出、进度（包括已完成与未结）、试过没成的办法、下一步和证据位置；更正、已定事实和授权更新到原处。试过没成的办法指为同一个目标换过的一类做法（换思路、换验收办法算，换人、换参数不算），每类一句：做了什么、哪项验收没过或哪个数没降；还在跑、没验完、被叫停的不算没成。单条毛病的记在毛病账那一行，没进账的卡点记在短任务单，整个工程迟迟不收敛的按工程与交付“验收只证明结果”记。交接、设计、施工文档在原处改成现状；毛病账一条毛病一行，只写这条现在的状态、轮次、试过没成的办法和证据位置，经过不往里堆；排查账和每批收尾的数是按时间追加的流水，一次一行，不改旧行（写错了追加一行更正，写明更正哪一行）；手写的交接和接续只留最新一份，写了新的就删旧的（带日期的汇报、回执和证据照旧保留）；不另建“本人原话”稿、不贴聊天原文。摘要和计划不产生新需求；经验、决定和必要事实按共享经验的落点归位。简单任务不机械建文档，不建全景个人库或新的记忆服务，不记录隐藏推理。

README 只给 AI 和维护使用，简短列出现行入口，不再另写一份给本人看的长文档。给本人看的说明和指南统一由网站 wly0829.cn 从各自唯一来源生成。急救步骤不上网站：网站不再单设急救页（本人 2026-11-13 定：他从没看过，不要了），急救步骤只留 PCConfig 的来源给 AI 读，加上 F 盘救急 U 盘和 G/H 备份盘根目录的短说明。本人日常只看实况，见能力与运行方式“本人只看实况”。项目的 AGENTS 只写这个项目真正不同的地方；实现或入口变了、影响到它写的承诺时同步更新。网站取材和去副本按下一节执行。

第三方 CLI 长任务由 AICLI 和具体项目负责接续，不再交给个人技能；到自然边界保存检查点，恢复时先接当前产出和未结事项，再按下一步需要读取项目规则、Git 状态和源码。

通过电脑 MCP 操作项目，以及个人项目中需要电脑智能体执行的后续事项，归入电脑端对应项目现有需求、待办或接续入口，由电脑 Codex／Claude 在相应操作时承接并提醒。无论本人从手机还是通过 MCP 发起，包括媒体库按需更新，都不在 ChatGPT 新增任务，也不另建 ChatGPT 定时提醒来代替项目接续；本人另行明确指定提醒方式时按新指示。记录后续条件不等于立即执行，也不等于获准向另一个现有会话发送任务。

碰到项目和压缩后先读哪份

约法和导航在各家入口里，压缩后原样还在，不另行重灌、不要求重读（Antigravity 压缩后是否原样还在见Antigravity 适配）。对话中途读过的专题、项目规则和攻略，以及 Codex 的技能正文，压缩后不保证还在；漏读项目做法的根子多在没认出这次在做哪个项目，不在压缩本身。所以程序按 AI 实际碰到的东西认项目：读写了登记项目目录里的文件、用了登记给该项目的技能，以及本人消息里提到项目名。这几样对所有项目一样适用；不为单个项目写专门的认法（比如按某项目的联系人名单认），这些痕迹之外的由 AI 自己判断在做哪个项目。同一对话第一次碰到某项目时给 AI 一行：项目规则位置和该项目规则开头“做什么之前先读哪份”的短表；每次压缩后再给一行：这次对话碰过的项目（同样带短表）、用过的技能、读过的专题，有任务状态文件时再给它的位置；这一行由 Claude、Codex 根会话的钩子给，Antigravity 没有压缩事件，做不到（见Antigravity 适配）。只给位置不给全文，只提醒不拦，同一项目同一对话不逐条重复。AI 在下一步用到哪份时重读哪份。短表由各项目在自己规则开头维护，只写位置，做法仍以所指文件为准；没出过漏读问题的项目不必补。

压缩前后

三家根会话开对话、恢复和压缩以后，上下文里没有时，钩子只递位置（普通消息不带）：这个对话在哪个登记过的工程、它的《他要什么》第几版在哪（工程的《他要什么》由翻译官照本人的话写，见模型清单“读懂人的话”一行）、工程卡和任务进度在哪；不再带本人话摘要和以前的原话，也不把原话当依据。压缩后、动手做这个工程的事之前先读《他要什么》，再照定稿、交接和任务进度接着做，工程卡里列了账的（毛病账、排查账这类）也照账接着做；之后本人新说的话优先。每轮的本人消息清单和连发防漏答照常。根会话压缩前更新已有的短任务状态，没有入口时用本任务的 work/task-state.md（这份给接手的人读；要钩子带回它的位置，用已绑定的入口或 task-state.json）。压缩后留下的内容里还有这几句就不再补：Claude 压缩前把它交给摘要；Antigravity 没有压缩事件，按对话里新出现的压缩摘要判断。

纯技术工作不依赖资料解锁（约法 L18）。资料锁着或未知、又到了压缩预警时，根会话若已确认整个现有会话确为纯技术，可用技术范围登记记录当前原话边界及确为技术资料的证据位置，命令见该运维文档。登记由 AI 做，不请本人另行批准；新增或改写的真人消息不继承旧判断。旧历史混有私人内容或范围不明时不登记整段技术，仍走原资料入口，不先读私人历史来补这个判断。该登记不解锁资料、不放行私人库；未读取的部分继续列为未覆盖。

重大动作仍按原把关规则。

程序入口、暂停开关和各家实际支持的事件见上下文 Hook 运维，Antigravity 的见Antigravity 适配。纯模型主动换窗与原生压缩分别验收，不能从一种事件的成功推定另一种也已接通。

一样东西只存一处

规则、事实、决定和本人原话各只存一处，就是上面“事实找谁”分给它的家；本人原话存原话存档，本人以后要遵守的做法存规则，本人自己的事实存理解库明示。别处用到时，写一句现行结论并指向那一处（路径、章节或编号），不整段抄。会变的数（版本、数量、剩余空间、“第几行”、部署或运行状态）的家是能查到它的命令、配置或系统本身：说明、规则、手册这类长期文档写去哪查，非写不可就注明是哪天看到的；带日期的决定记录、汇报、计划和评测保留当时的值，不回头改。发现副本时，先把副本里更新或多出来的内容并回它的家，再把副本改成指针。由工具从唯一来源生成、并核对一致的副本（例如规则发布快照、装到用户目录的入口文件、网站生成的说明页面）不算副本。急救步骤的来源在 PCConfig，网站不再照它生成急救页；给本人看的内容不再在仓库 README 或另一份长指南里手写维护。过时的历史报告和设计稿不改写，没人再用就移出工作区。跨文件引用写链接加章节名或条目名，不写“第几条”，重新编号时才不会悄悄指错。跨文件查重用 Find-DuplicateContent.ps1，结果逐组判断后再收副本；项目里由程序生成并核对的副本和带日期的记录，在项目根 .duplicate-content-exceptions.json 的 non_copies 声明一次，不再算副本。指不到的链接和章节用 Test-DocReferences.ps1 查。写死的会变机器值（没登记的本机端口、软件版本号、按本机钟点写的时间、“当前状态”写法）用 PCConfig 的 Find-VolatileFacts.ps1 找：没登记的本机端口在 PCConfig 测试里直接报错，其余候选由每周体检逐条判断。

把几处现行结论合成一段的汇总（例如理解库核心画像、当前处境卡、实况条目标题、项目首页）也算引用：每条带“截至哪天”并指向家；办事进度、计划、用药、金额这类会变的状态只写意义和指向，不写成现在时。改了家的任务负责找出直接引用它的汇总，在同一任务里更新；做不到的由下次全量更新的收尾核对补上。能用程序查的交给程序（例如理解库 card-lint 的 h、i 类），查出来就算待处理，不能只列出来不算数。

写之前先查

写本人的事前先用 pwsh -NoProfile -File E:\.agents\tools\Find-ExistingRecord.ps1 -Term <词,词> 查已有记录，查法和结果处理见命令帮助及输出。

共享经验的落点

Claude、Codex 的自动记忆都已关闭，Antigravity 的还没核实（见Antigravity 适配）；不往各自的记忆区写内容，关闭配置见各自适配专题。规则写现在怎么做，本人定的句子留半句为什么；改过几次、以前怎么定的放 Git 历史。主持平时只用当前对话、工程的《他要什么》和相应定稿；只有发布批准（由程序核对出处）、核实一句话是不是本人说的、或确需原样发出去时，才按源消息编号取原话。本人明确要核一句旧话又没有编号，先定位它出自的对话或证据，再按编号核实。当前对话内按需要看当时在回答什么、后来有没有改口、这句是要求还是判断；本人亲历和自己的情况以本人为准，外部事实和原因靠原始材料和实际结果核实。查不到不等于本人没说过，看不到前后文就只当线索。AI 转述只是 AI 的理解；照原话做错了，仍算理解错。

原话。 三家宿主只将核实为本人输入的正文原样存档；钩子注入、程序派单与自动续作不写入本人原话目录。旧非本人记录移到旁边保留。即时存档和后台补漏沿现有自动任务处理，不受资料锁限制；读取仍受资料访问规则约束。原话档案不进默认搜索，跨对话仅按编号取。位置、格式和补存见运维说明。

跨任务查旧资料，按现有项目的定稿、办事记录和证据位置接续；任务单不贴旧原话；本人这次说的那句照派活技能给原文。只存档的会话留给原会话接续和按编号核实。

要不要记，收尾时再想，大部分不用记。 和开场那一页“被我纠正、质疑……”那段一致：

  • 只管这一次的：提问、好奇、本次安排和选项回答、当场改了就完的纠正、“这次先别……”、对眼前这一张图、一个设计、一个视频的评价。留在对话和任务状态里，不写任何地方；这件东西换个对话还要接着做、到时候找不到这句话的，记到它自己的文件里。
  • 下次不看规矩也不会再错的：假如规则里没有这一句，AI 在这件事上也不会做错（常识，或者现有规则已经能推出来），那它只是本人当时提醒注意，不记；反复出错的不算这一类，按下面“出了错修根因”办。
  • 以后还会用到、现有做法又没覆盖的：禁令、长期授权、长期要求和偏好。记到做那件事时读得到的地方（见下面“写进哪一层”），提交说明写源消息 UUID，回复里一句话说明写在哪。
  • 有期限的写明“至 YYYY-MM-DD”，到期由每周规矩复核删掉；跟型号代际有关的写进模型清单，随换代更新。

什么能删。 重复、过时或 AI 自己加的做法可以自主删改；本人仍然要的结果、禁令和授权范围，不因挪到专题、技能或项目就变成 AI 可以取消的；本人定过的纯技术做法，前提变了或有明显更好的，照约法直接改并说清改了什么；涉及取舍、花钱、删唯一数据的，带着建议请他定。施工碰到和约法打架的具体做法，按约法顺手改掉，说清改了哪句。

怎么写规矩（本人定的原文，原在约法）。

先判断有没有意义、有没有必要： 加或改一句规则之前，先想清这句让我得到什么、不写会出什么事、有没有更省的办法（比如改一句现有的就够），说不出来就不写；我要求加的也一样，判断不该加就当场说清为什么，我听完还坚持的照写；给我看拟的句子时，用“有意义”“有必要”或“没意义”“没必要”把结论说出来。

要求加在做那件事的必经之路上，AI 走到那一步一定读得到： 我的事实记个人项目；某个项目的记那个项目；工具怎么用记技能，技能的一句话简介要写清，让 AI 进入那件事必定发现；这一代模型的毛病写结尾那段，模型清单 E:\.agents\config\model-roster.json 的 limits 记一行。不图省事加进这一页或全局规则：几乎每次都用得上、放到私人聊天、正式文书、修 bug、做视频都不带偏的才写进这一页，跨项目又没有更近必经之路的才写进全局规则；挪走会影响 AI 判断或比较重要的不挪。要加，给我看那句时说清必经之路是哪、为什么那里不够。要限制模型能力的话，写明限制哪个型号，句子放结尾那段或做那件事时读得到的地方（派活技能、程序说的话），模型清单 limits 记一行指过去；有我的原话或证据说明不限制大概率出问题、这句大概率解决得了，才写。值得写的主要是三种：模型不可能知道的事（关于我、我的电脑和工具、哪些要我点头）；我要的做法和厂商默认不一样、又能挂在一个看得见的动作上的（比如验证过就直接提交推送、代码施工按模型清单「写代码、改脚本、修 bug、排障」一行）；撤不回的事的把关。劝它想得更全、更谨慎、更独立的话不写，厂商已经在推的方向也不重复写：写了改变不了它，还占地方、留借口，这类毛病靠我当场一句话，或者换做法。写规矩写我要的结果和为什么（我定的句子留半句为什么，免得后来的 AI 改回去），界线尽量交给模型临场判断，别靠列情况、写死步骤去补（写死的总有没想到的情况）；条件、门槛、例外只写在一处，别处要提就指过去，写节名不写条号；同一句话两家读法不一样：GPT 往严了读，“别……”和门槛会被它放大，要它做的得正面写出来；Claude 往宽了读，例外和“可以”会被它放大，例外要写窄。共用的句子两种读法各过一遍，只关某一家的（那家型号自己的毛病、那家独有的机制）才只写进那家的结尾（本人 2026-11-19：没点名哪一家的要求三家都照做）；也别写成到哪都算的绝对话；也别把规矩的说法绑在哪个程序眼下怎么做上（谁出数、用哪条命令、怎么算），我话里提到程序也一样：程序随时会改，规矩只写要的结果，做法写在程序自己的说明里。写之前先读那个地方，已有同一件事的就改原句，同一件事写在几处的一起改，没有才补必要的一句。新句要和别处的规矩对得上。新句和旧句打架，一般新句优先，AI 自己裁定，别一打架就停下来等我。旧句让路是因为新句优先，不是认定旧句错；看旧句本身和它留的半句为什么就行，不用去翻它当初怎么定的。讲的是同一件事，就改掉或删掉旧句；新句是一个全面范围、旧句是其中的例外，一般带着旧句，写成新句的例外。旧句看起来也有道理、拿不准该不该让它让路，用选项问我，不依赖它的接着做。动禁令和授权范围照样先问我。我原话说清了的直接记，做完说一声；这一页和结尾那段例外，先给我看这句，我点头才上。你另加的要求、新程序、改变适用范围的，也先给我看。原话程序自动存档，不用你抄。

写进哪一层：

  • 话里提到某个项目自己的东西（这个视频、这份材料、这个网站、这个仓库），写进那个项目的 AGENTS.md 或项目文档。
  • 只讲 AI 怎么说话、怎么干活、怎么用工具和模型，不涉及哪个项目的东西，写进本仓库对应专题：改源码，随任务收尾按规则发布发布；要改开场那一页和各家入口结尾那段的，先给本人看这句，他点头才上。
  • 拿不准就放说这句话的那个项目。放窄了，别的项目最多再犯一次、本人再说一次；放宽了，所有项目都会被误伤。同一件事在第二个项目又说到，或者本人说了“所有项目”“以后都”，挪到做那件事时一定读得到的更近的地方：工具用法进那个技能，没有更近的才进全局规则。挪完删掉项目里那条。对 AI 做的东西说的审美上的话不往外挪，照约法审美那句办。

出了错修根因，不记错误。 出了错默认查清根因并修掉，本人说“只需要快速恢复”这类话时才只做恢复；向本人提修复办法时先说是根治还是缓解，缓解要说为什么值得先做。本人的纠正和抱怨（“怎么又出问题了”）、具体出了什么错，都不另外记录，原话存档里有。防再犯先分清是下面哪一类，按那一类办，不是越往程序里修越好：

  • 能在系统里修掉的（工具的错、缺自动化、默认值不对、少一步检查）：改代码、工具或配置，加测试防回归。修好了就不用谁记住。
  • 是 AI 做某件事漏了一步：把这一步写进那件事的做法文档或技能，做那件事时才读到。这是改流程，不是记错误。
  • 是模型判断上的事（说到多具体、怎么取舍主次）：该不该说得具体要看场合，交给模型自己判断，不另加规则文字，也不默认加复核流程；但现有句子把判断推歪了的，改那几句原句。本人当场说“似是而非”“答偏了”，先弄清偏在哪个方向，只查这个方向上答案靠的事实，拆开重答；同一件事反复做不好，才换做法（换作者、换模型或提高档位）。
  • 一直加载的全局和项目规则只放几乎每次都用得上的，不往里堆场景细节和错误清单。

不错误抽象：

  • 照原话的意思、条件和范围写。原话里有“因为……”“除非……”“……的时候”，规则里保留；不把当时那件事的具体做法升格成通用原则。
  • 禁令写明是禁令，附时间和源消息 UUID 备查，不附原句；偏离前先问本人。
  • 新旧规则怎么改、怎么处理冲突，见本节“怎么写规矩”。本人最新的话改了要求的，照约法“被我纠正”那段办，改定后删掉旧的。

旧决定月卷只是历史。 docs/owner-decisions/ 不再新增，不注入，也不当规则读；跟现行规则冲突时以规则为准。子代理不改规则、不记原话，照派单做。

内容 写到哪里
怎么跟本人说话 通用说话规矩在约法 L1–L6；只和本人有关的（例如本人状态很差时怎么说）进理解库；某个技能或项目的写法（汇报页、实况、拟消息等）进那个技能或项目。新增时先查同类并合并，写清本人要的结果和适用范围，保留源消息 UUID 以便按需查原文。
Claude、Codex 或 Antigravity 自己工具的坑 对应的Claude 适配、Codex 适配或Antigravity 适配。
某个项目的事 该项目的 AGENTS.md 或相关文档。
本人的原话 原话存档，钩子自动存，AI 不手抄。
本人以后要遵守的做法 按上面“写进哪一层”，记到做那件事时读得到的地方。
拿不准放哪里 先写进最接近的那份规则，发布规则时再挪；本人以后要遵守的做法不放待办。

每周规矩复核是实况自动任务里的一类，每周跑一次，做什么以派活程序里这一类的提示为准（定位见 E:\PCConfig\registries\task_purpose_catalog.json）：查这周改过的、给 AI 看的字（约法、入口、专题、技能、项目规则、运行手册、钩子里给模型看的话）有没有和别处说反，顺带跑断链、重复内容、写死的易变数字和型号、过期的“至某日”这些零碎检查。它不读原话、不把原话写成规则；没跟上新说法的旧句自己改（改专题里讲 AI 怎么做事的句子，照约法先派没看过的子代理对全文查打不打架），约法、入口结尾那段、三个受保护专题和禁令、授权范围不改，登“要你选”，题干写两句原文和出处。实况上的说法对不对由“实况每周对一遍”查。反复出现而根因没修掉的问题交自动修理。规矩复核按任务定义跑时是后台自动任务，资料锁着、到期或状态不明都照常取用私人内容；本人在对话里让 AI 跑一轮时仍按资料锁办，见《个人资料与数据处理》“公开内容和后台自动任务”。不把 AI 的猜测写成本人决定。网站不单设每周复核，更新按能力与运行方式“汇报、网站和自动运行的东西”。
