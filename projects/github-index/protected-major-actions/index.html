这项功能怎样使用

用途与实际影响

为什么需要它

仓库改名、改变公开范围或删历史会影响别人看到什么、还能找回什么；目标错一个字就可能改错仓库。系统只对这一项真实变化做判断，只有删库、转移、改成公开、新建公开库才请本人验证，不把每次普通提交都叫来本人验证。

举个实际例子

比如我说“把仓库改名，但公开性和默认分支都别动”。系统先固定旧名称、仓库唯一 ID、可见性、默认分支，并确认新名称没有冲突；改名不属于要本人验证的四类，所以直接只执行改名。做完立即从新名称回读同一仓库 ID，并确认可见性和默认分支原样不动。任何目标漂移都会停下，而不是顺手改 owner 或其他设置。

最后我会得到什么

拿到明确的变更目标、执行前后状态以及是否还需本人验证；删库或转移前，我还会先看到一份损失清单：哪些 Git 内容已经保全、哪些网页内容只列了名字、哪些根本不在备份里。执行后从仓库现场核对；结果暂时不明时先查仓库，不重复发起可能已经发生的重大动作。

结果怎么看
正常时

目标仓库、旧状态、内容保全与必要确认都吻合后，只执行点名的这一项，并回读真实仓库。

发现问题时

目标变化、内容保全失败或远端部分完成时停下：保全失败直接停；已发生的结果保留，只补真正没完成的步骤。

入口不可用或证据不足时

仓库现场读不到，或需要本人验证的动作遇到验证入口不可用时，停这项重大动作；普通只读与安全本地工作仍可继续。

关键规则与设计选择
1
普通本地读取、可逆编辑、定向提交和已授权正常推送不自动升级为重大动作。
2
固定 10 种操作：git-local 4 种（delete-local-ref、delete-remote-ref、force-update-local-ref、replace-remote-url），github-api 6 种（create-repository、rename-repository、set-visibility、set-default-branch、delete-repository、transfer-repository）；不开放任意 shell 或 API。
3
create-repository 可在当前账号下建空的 PRIVATE（私有） 或 PUBLIC（公开） 仓库；配置 origin、首次 normal push、默认分支收口和索引登记随后由普通 Git 分别完成，建库不等于项目已经发布。
4
每种动作使用自己的精确参数、preimage 和 read-back（正式回读）；改名不能顺带改 owner/visibility/default branch（分支），替换 remote（远端仓库） URL 不能变成任意 Git 命令。
5
是否需要本人验证按 GitHub 四类规则：删库、转移、非公开改公开、新建公开库需要有效的无限制授权，没有就本人验证一次；个人资料已解锁不能替代这次专门验证。
6
Passkey（通行密钥）、TOTP（动态验证码）、Recovery（恢复码）、Account（账号验证）是四类因子；Google 和 Microsoft 只是 Account 类别的不同 Provider（提供方）。
7
改名、改默认分支、改成私有、新建私有、更换本人账号下的远端地址，以及内容已被保留的 ref 删除/改写，不请本人验证，也不查无限制授权、资料期或密码中心；内容保全失败就直接停，不改成“请本人验证后继续”。这只是程序分支，调用前合格的 AI 仍按活动规则判断真实后果。
8
已证层：当前源码和用隔离 Git、模拟 GitHub 与验证服务的测试定义存在；9 月 27 日重写后没有实际使用记录。旧的 C 盘第 79 代、E126/E131 和来源 bfc9f3f 只作历史，不证明现在的 10 类动作。

技术实现与依据（二）
当前怎样实现
  • 旧的提案/能力票据链已退役（2026-09-27）。　原来 Prepare 冻结提案、AuthorizeMajorAction 授权、30 秒单次 Consume 后执行，并绑定签名、nonce（一次性随机凭据）和执行器哈希；现在脚本里没有这些步骤。
  • 现行入口 Invoke-ProtectedGitHubMajorAction.ps1（896 行，最低 PowerShell 7.5，结果 schema github-local-index.protected-major-action-result.v2）只收 Operation、Repository、RepoPath、ArgumentsPath，以及可选的 DryRun 和验证方式，一次调用 Invoke-GitHubAction。
  • 需要本人验证的分支调用已安装的 OwnerTakeover Check 和 SecretBroker VerifyAuthority，核对回执里的 highest_authority_verified 与 human_factor_performed，执行前再重读一次实际目标。
  • 验证方式选 Auto 时不传 AuthorityFactor，由现役密码中心在四类方式里选一种；Runtime 身份不能顶替重大动作的本人验证；已有有效的无限制授权就不重复弹出。

  • create-repository 绑定 expected_absent、expected_local_branch、expected_head_oid 和 clean 工作树；PUBLIC（公开） 走重大动作验证和首次公开授权，PRIVATE（私有） 不验证。
  • rename-repository 冻结旧/新 slug、同一 id/node_id、visibility（公开或私有属性） 和 default branch（分支）；新 slug 必须 absent，回读必须确认 identity 与除名称外的字段不变。

技术实现与依据（三）
1
从 10 种固定操作中选一种，把精确仓库/ref/remote、旧值和目标值写进参数 JSON，不接受自由命令
2
核对仓库身份、预期字段和同一 id/node_id；ref 类操作先证实原提交另有分支或标签保留
  • 删除远端 ref 用精确 URL 加旧 OID 的 force-with-lease，防止期间别人新推的提交被误删。
  • 删库和转移固定先用同一命令加 DryRun 预演，由调用的 AI 在正式执行前向本人讲清目标、本地 Git 保全结果、网页独有内容清单、没枚举的类别和损失范围；再去掉 DryRun 正式调用并重新读现场。已知内容或去向变了，就重新预演、重新讲。
  • 这两次调用是合同里调用 AI 必须遵守的工作规则：脚本不保存前一次预演的票据，也不强制匹配，不能说成绕不过去的安全墙。DryRun 不查无限制授权、不弹验证、不改 GitHub，但删库/转移的预演会拉取、补全 Git 对象并建保全 refs，所以不是严格零写。
  • 删库/转移的 Git 保全：浅克隆先补全，拉取全部分支、标签和历史并核对 OID，缺的本地分支或标签补建，同名但分叉的不覆盖；远端最新提交保存在 refs/backup/github-major-action/<owner/repo>/objects/<oid>。
  • Git 以外的内容：issue（含 PR）、Release、发布包按全部分页列出标题、名称和链接，只是清单，没有备份内容；Wiki、讨论、项目、Actions 只给入口和已知开关，内容没枚举；Git LFS 外部对象、子模块仓库、Actions 产物和包注册表不在 Git 副本里。工具打印出来不等于本人已看过，损失边界要由 AI 具体讲给本人。
  • 网页只展示公开安全的动作类别、规则差异和证据层，不公开因子秘密、账号身份、内部请求材料或可重放参数。

  • 删库和转移固定先用同一命令加 DryRun 预演，由调用的 AI 在正式执行前向本人讲清目标、本地 Git 保全结果、网页独有内容清单、没枚举的类别和损失范围；再去掉 DryRun 正式调用并重新读现场。已知内容或去向变了，就重新预演、重新讲。
  • 这两次调用是合同里调用 AI 必须遵守的工作规则：脚本不保存前一次预演的票据，也不强制匹配，不能说成绕不过去的安全墙。DryRun 不查无限制授权、不弹验证、不改 GitHub，但删库/转移的预演会拉取、补全 Git 对象并建保全 refs，所以不是严格零写。
  • 删库/转移的 Git 保全：浅克隆先补全，拉取全部分支、标签和历史并核对 OID，缺的本地分支或标签补建，同名但分叉的不覆盖；远端最新提交保存在 refs/backup/github-major-action/<owner/repo>/objects/<oid>。
  • Git 以外的内容：issue（含 PR）、Release、发布包按全部分页列出标题、名称和链接，只是清单，没有备份内容；Wiki、讨论、项目、Actions 只给入口和已知开关，内容没枚举；Git LFS 外部对象、子模块仓库、Actions 产物和包注册表不在 Git 副本里。工具打印出来不等于本人已看过，损失边界要由 AI 具体讲给本人。
  • 网页只展示公开安全的动作类别、规则差异和证据层，不公开因子秘密、账号身份、内部请求材料或可重放参数。
