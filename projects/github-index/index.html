为什么这样设计
总表只是导航，不是事实。
登记会过时。动手前再读一次真实的 .git 和 GitHub；不这样，搬过家、改过名的目录会被当成原来那个仓库。
能传、能公开、我同意，三件事分开。
网络和分支没问题，不等于内容适合公开；内容能公开，也不等于我同意发布。三样分开判断，谁也推不出谁。“我同意”不是每次推送都来问我：已经在用的仓库，验证过的提交和正常推送本来就在我的长期授权里；第一次公开到一个新地方、第一次发正式版本或强推，才另外问我。
进了 GitHub 主线才算交付。
推到临时分支、本地 main 提交了，都不算完；要在 GitHub 上的默认分支里找得到这次的提交。
一样东西只存一处。
冻结名单（约法 L24）和公开分级从生效的规则读，计划任务交给电脑配置与恢复，这里不再抄一份。
上不上网站，单独登记。
哪些项目上网站、叫什么名字，写在单独的一份登记里，不会被总表刷新覆盖；新仓库默认不上，忘了登记，测试会拦下来。
大动作入口不假装是一道安全墙。
删库、改公开的入口一度写到 2,746 行，还配了提交前拦密钥的检查，看着很严，其实挡不住一个已经登录 GitHub 的程序直接删库，维护却很重。9 月 27 日我定了：入口瘦身，承认靠 AI 守规矩。现在 894 行，只做几件实事：核对目标、删库前保全并先预演给我看、该验证时请我验证、做完读回；重写后还没有用过的记录，所以功能表里标待验收。拦密钥的检查拆了：AI 对密钥本来就警觉，密钥都在密码中心。

亮点
一个仓库，九个工作目录

几个 AI 同时干活，各开各的临时工作目录。9 月 28 日凌晨，电脑配置与恢复一个仓库就开着 9 个。收尾只看当前窗口，别的目录里做完没合的活就会被忘掉，或者被当成垃圾清掉。总索引把每条分支都拿去和 GitHub 上的主线比：内容已进主线的标“残留，可以收”；有独有提交的写明“主线缺 N 个提交”，先并进去；有没提交改动的只提醒核对，不碰别人的东西。那天它就找出一条比主线多 9 个提交的临时分支。

读不出来，不等于对不上

GitHub 偶尔连不上，Git 命令偶尔失败。要是把“读失败”当成“身份对不上”，AI 可能就去改远端地址，或者认定这是别的仓库。9 月 18 日起两种结论分开：读失败只算“不知道”，停写入和推送、不停查看，也不因为一条命令失败就整个停工；真读到了而且和登记不一样，才算冲突。
