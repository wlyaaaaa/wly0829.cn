# 规则、合同与事实 Owner（事实责任源）

〔回到项目 → AI 规则与技能基座〕　〔复制 AI 续作说明〕

.agents · 功能说明

AI 不会拿上个月的报告当今天的现场，也不会跑到错误仓库执行一套看似正确的命令；业务、Git、机器和 Agent 规则各回到真正负责它们的来源。

**当前情况：**当前共同规则已经生效，任务可按问题找到正确的项目与事实来源；这不代表每个项目的实际功能都已验收。

具体测试保留各自日期，页面不实时探测运行状态。

项目源码：私有仓库，源码未公开；用法与技术说明可在下面阅读。

## 这项功能怎样使用

用途与实际影响

## 为什么需要它

一项任务里常会同时出现这轮新要求、项目自己的规矩、全局规则、历史说明和当前状态。解释权不清楚，AI 就可能让旧计划盖过用户更正，或用通用做法盖过项目真实验收。

## 举个实际例子

我会直接说：“按这个项目自己的测试把问题修好，别拿上个月的报告当现状；如果发布状态和电脑状态对不上，就分别查清。”系统以我这句话为准，再看约法和项目自己的规则；需要仓库事实才查 Git 总索引，需要机器事实才查 PCConfig。我拿到的是各来源的当前结论，不是一份拼出来的故事。

## 最后我会得到什么

任务会从有效规则和当前事实出发。若两个来源真的冲突，系统只停受影响的判断，告诉我冲突在哪里、该由谁裁定，以及其余工作还能不能继续。

## 结果怎么看

## 正常时

这次要求、项目约定和现场事实对得上时，按项目自己的方式继续。

## 发现问题时

两份来源确实冲突时只停依赖它的步骤，说明应该由谁核实。

## 入口不可用或证据不足时

必要规则或现场暂时读不到时写清无法判断，不让旧报告冒充现在。

## 从哪里开始

在已接入活动 E 规则的 AI 对话中说出项目和具体问题，请它按当前规则处理。

## 需要准备什么

- 项目名称与目标

- 这轮更正或限制

## 从开始到拿到结果

1. **先说清本次要求与项目**　AI 先核对这轮原话、活动规则和项目自身约定，找到这件事由谁解释。

2. **把事实交给正确来源**　代码仓库的发布状态查 GitHub 总索引，电脑路径和任务查 PCConfig，具体功能问所属项目；旧报告只作线索。

3. **交回决定与冲突**　说明能继续的动作、确切依据；若两份有效来源冲突，只暂停受影响的判断并指出下一处取证入口。

## 关键规则与设计选择

1. 谁优先：我当下明确说的话 > 约法 > AI 的其他规则；其他规则之间，适用的项目规则先于本仓库专题，技能和参考资料最低。

2. 项目规则管自己的业务、命令、测试、兼容和生成区，可以在项目内收紧做法；但项目不能产生授权、取消已有的长期授权，也不能自行收紧公开 L1/L2 内容。

3. 需要 Git 或机器动态事实时，改去对应控制面现场读取；导航、README、旧报告和计划不能顶替。

4. 只有当前问题真正触发时才展开专题；来源冲突无法同时满足时停止，不用猜测拼接。

## 出问题时（一）

解决什么

当本人要求、约法、项目规则、历史文档和现场状态同时存在时，必须有一套稳定方法判断谁拥有事实、哪一层优先，否则模型会把旧报告当规则、用全局原则覆盖项目业务，或者一次性加载所有材料后丢失注意力。

## 边界

- README 和操作指南面向人，不是执行规则或动态权威。

- 合同目录只能选择候选正文，不能证明某个外部动作已发生。

- 全局规则不以统一为理由覆盖项目业务与测试；项目也不能借自己的规则扩大或取消授权。

- 兼容文件名和历史命名不能恢复已经退役的控制面。

- 项目分三档维护：新项目默认日常用、偶尔用的只修报错、存档的不维护。冻结名单只以活动 context-sources 专题为准，当前 11 个仓库条目；批量“全部项目”不包括它们，本人点名具体需求只处理该需求；冻结项目自己的计划任务停用，已有资料继续保留并由机器备份覆盖。

## 失败与恢复
