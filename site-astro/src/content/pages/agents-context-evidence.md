# 接着上次的工作，查清事实和完成状态

〔回到项目 → AI 规则与技能基座〕　〔复制 AI 续作说明〕

.agents · 功能说明

长任务会压缩、换手、跨好几天。它让 AI 接着做之前先找回我的原话、更正和授权，按真实项目和真实来源核对现状，收尾时对照我提过的每条要求交账；也避免拿代码、测试或部署成功代替真正可用。已经冻结的项目不会被批量维护带回施工。

**当前情况：**我的原话按月份原样存档（截至 10 月 23 日 08:40 共 1635 节）；现行要求有一张唯一的要求表，长任务收尾要逐条对账；对话压缩后会自动在后台排一次增量复核；接续时按真实项目定位，不按“最新”去猜。

项目源码：私有仓库，源码未公开；用法与技术说明可在下面阅读。

## 这项功能怎样使用

用途与实际影响

## 为什么需要它

长任务会经历对话压缩、换人接手和外部状态变化；源码、测试、安装、发布、公网与用户结果又各自证明不同的事。只看摘要或一个“通过”，很容易在过期前提上继续忙，或者悄悄漏掉我早先提过的要求。

## 举个实际例子

我可以说：“只检查 Git 总索引，别刷新引用，也别修。”系统只做这项零写入诊断，分别告诉我结构是否健康、现在能否收口。又比如一个长任务压缩了三次后我说“接着做”，AI 先读回最近的原话、现行要求和上次的任务状态，按项目位置找回原来的仓库和工作副本，再继续；压缩后的后台复核如果发现漏了某条要求，会提醒它补上。

## 最后我会得到什么

我会看到这次查了哪些真实来源、有没有改动，本地、远端和用户结果各自到哪一步；长任务收尾时，每条要求是做完了（附证据）、还是延后（附原因）。读不到的那一层保留“未知”和下次核对入口，不拿摘要补空白。

## 结果怎么看

## 正常时

所需来源可读、各层证据一致、要求表逐条对上时，形成一份能接手的当前结论。

## 发现问题时

摘要、源码、运行状态或外部回读冲突时，以现场责任来源为准，把冲突层单独列出，只停依赖它的判断；要求缺完成证据或延后原因时，长任务不让收尾。

## 入口不可用或证据不足时

必要来源读不到时，对应结论标成未知或明确阻断；不恢复退役的中央系统，也不从旧摘要猜现状。后台复核失败或超时，不推进已覆盖进度，原批续作。

## 从哪里开始

在原 AI 任务中说“接着做”并指出目标；新对话里明确说接续哪个项目，或点名只读诊断的项目与检查范围。

## 需要准备什么

- 原目标和已完成部分（或说“接着上次那个项目”）

- 想确认的状态层或项目

- 是否仅检查、不修复

## 从开始到拿到结果

1. **恢复本次目标**　AI 先找回我的原话、更正、确认结果和授权，读现行要求表和短任务状态，把它们和旧方案分开。

2. **向实际来源求证**　按真实项目位置找到仓库和工作副本，查看代码、仓库或电脑的当前状态；只检查时说明会不会刷新远端信息。

## 关键规则与设计选择

1. 普通单项目问题不进入全景控制面；跨责任来源的决定先读元数据，再展开必要正文。

2. 证据缺失或过期时降为“未知”，不是“通过”；设计、Git、机器运行和外部回读分开验证。

3. **原话唯一存档：** 新原话只写进月卷 `docs/owner-decisions/YYYY-MM.md`；旧 owner-decisions.md 只是导航，order.json 保原序。写入在共同的跨进程锁内校验 UTF-8 和换行、原样追加，记录时只写盘、不传 `--commit`，格式不对就拒写。禁令、纠正和长期授权当场写盘；其余在交付收尾或压缩前一次归位；两种都和要求登记一起在交付收尾或压缩前批量提交，不逐条提交，推送随任务正常收尾。后台每 3 小时只补已归档、或最后活动超过 3 小时且有未归位原话的根会话，源消息已被引用就跳过，资料锁着或未知时记录跳过、不解锁。钩子已存的本会话消息也算出处，标“本人原话（待归位）”，不因未分类、未写月卷或未提交报警。出处由根会话负责，派活不附原话清单，子代理不查出处、不报“无出处”。

4. **现行要求唯一表：** `requirements/register.jsonl`，按全局、项目、任务标签查询；每条有状态（现行、完成、被取代、撤回、延后）、来源消息编号和原话片段、完成证据或延后原因。登记同样只写盘，和决定一起批量提交。这是明确采用的现成要求表，不是“绝不建任何台账”。

5. **决定短投影：** 现行决定按分类生成短投影，上限 6,500 字节（UTF-8），不手抄长索引。

6. **长任务收尾对账：** Close 时缺要求、缺交付证据或缺延后原因，就拒绝收尾。

7. 压缩、交接、更正、反复失败或扩架构前先恢复原意；有冲突改方案，不改用户要求。

- **压缩后后台复核：** 每个新的主对话压缩边界只排一次，同一主对话最多一批，子代理压缩不递归，正常工作不等待。由 Sol（ultra）按新原话增量加旧的未结要求，检查遗漏、真实完成证据和擅改决定；本人原话出处由根会话认定，复核者不另查、不报“无出处”，只有禁令边界上的分类分歧作为提醒交回；普通提醒不阻塞。每批有效工作预算 8 分钟、短回报目标 500 字，是可调参数。失败、超时或资料缺口不推进已覆盖进度，原批续作，不无限新建替身。资料锁着时，只有主对话已确认整段是纯技术工作，才按已有的技术范围精确登记放行。

- **按真实项目接续：** project_locator 读取 Git 导航里的展示名、仓库标识、地址和登记路径，再核本地 Git 的远端和仓库根；同名给候选，读不到不猜。project_task_context 保存真实项目、工作副本、材料、产出和状态入口及观察时间，压缩后重读。只说“继续”就用当前绑定；新对话明确接续时查唯一匹配，多个给候选；已关闭、已完成、已停止的不自动续。

## 出问题时（一）

解决什么

长任务会压缩，责任方会变化，同一结论又可能来自文档、源码、测试、运行时或外部回执。系统要让重要状态可重建，防止把摘要、历史命名或某一层“通过”当成全部完成，也防止压缩后悄悄丢掉早先的要求。

## 边界

- 普通单项目问题不机械进入三控制面全景。

- Doctor 默认不刷新远端；显式 Live 可能写本地 Git 引用，必须明示。Doctor 不修复、不安装、不改工作树或计划任务，也不提交推送。

- 兼容名称不恢复已退役的第四基座或中央个人上下文。

- 续作状态不保存秘密、隐藏推理和无关私人内容；后台复核在资料锁着时不借工作目录放行私人历史。

- 测试、回执和状态字段不能代替用户看得见的验收；短时通过不能证明长程不偏离原意。

## 失败与恢复

| 情况 | 怎么办 |
| --- | --- |
| Doctor 检查项无效或超出所选范围 | 在读取任何提供器路径前拒绝；缩小到正确范围，不自动补成全量。 |
| 健康为 warn 但 Git 收口为 block | 保留两个结论和原因，补证据或处理冲突，不把退出码 0 当可以发布。 |

## 出问题时（二）

| 情况 | 怎么办 |
| --- | --- |
| 后台复核失败、超时或缺资料 | 不推进已覆盖进度，原批续作；不新建替身。 |
| 长任务收尾时有要求缺证据 | 拒绝收尾，补完成证据或写明延后原因。 |
| 项目名对应多个仓库 | 列出候选让我选，不按最新猜。 |
| 摘要或方案与原意冲突 | 恢复原话、更正和授权，改方案不改要求。 |
| 证据过期 | 降为历史或未知，重做最小必要回读。 |

## 与其他模块的关系

本模块把其他模块的结论放进正确证据层，保证长任务和压缩后不靠记忆续写；授权由“授权与本人接管”管，派子代理由能力路由管。原来的工作树热镜像已退役，不再作为恢复层。
