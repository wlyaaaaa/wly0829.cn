## 这项功能怎样使用

用途与实际影响

## 为什么需要它

配置和记忆小、适合按版本对比；会话数据库大且一直在变，需要另一条快照路径。分开保存，一条链失败时就不会误报全部完成。台式机这部分现在交给开发配置备份统一管，笔记本因为要上云，仍走这条更严格的白名单。

## 举个实际例子

我说：“笔记本的 Codex 设置和项目记忆也要备份，别混进台式机的。”笔记本按自己的配置档运行：先在本机存安全快照，再写到已绑定的加密 USB，最后推到它独占的云分支。没插 USB 就不假造新的冷副本时间，云端失败也不抹掉本机结果。

## 最后我会得到什么

我得到这台电脑的设置与记忆副本，以及云端是否真的收到的单独结果。台式机要找 9 月 28 日以前的旧版本，去原快照留档找；要现在的配置，去开发配置备份。换机放回后，还要确认 Codex 登录和实际工作能继续。

## 结果怎么看

## 正常时

笔记本选中的小文件在本机和 USB 核对后，云端是否收到另给结论；只有新读的远端引用和本地 HEAD 一致，才写云端完成。

## 发现问题时

云端落后或冲突时保留已核对的本机副本，拒绝提交和推送；不把 Git 失败说成整层成功。

## 入口不可用或证据不足时

来源、USB 或私有仓库读不到时停对应那一层，说明哪些材料仍留在本机。有人照旧页找台式机的“每天小配置备份”，AI 会说明它已停用并指向开发配置备份。

## 从哪里开始

在已接入的 AI 对话中说要备份或找回 Codex 设置、Skills 或记忆，并指出是哪台电脑：笔记本走本模块，台式机现在的配置走开发配置备份，9 月 28 日以前的台式机旧版本在留档里找。

## 需要准备什么

- 目标电脑和它的配置档

- 要保护的配置或记忆类别

- 笔记本：已绑定的加密 USB

## 从开始到拿到结果

1. **选白名单**　按这台电脑的配置档挑小型配置和记忆，并转成可上云的安全形式；认证、会话和数据库不进这条线。

2. **先存本机，再存 USB**　形成并核对本机安全快照，再写到加密 USB 冷副本；后面每一步都从这份已捕获的快照取，不回头重读活文件。

3. **回读每层**　说明新本机点、USB 和云端是否真的收到以及排除项；网络失败保留已核对的本机结果。

## 技术实现与依据（一）

这里保留实现、关键条件、精确入口、历史记录和验证结果。

## 关键规则与设计选择

1. 笔记本当前不原样上传：AGENTS 转成惰性的 `global-policy.md`（恢复时才拷回 AGENTS），config.toml 经 Python 标准库 tomllib 投影成 `config.safe.json`；agents 映射为 agent-definitions，memories 只准入指定 Markdown、扩展和技能笔记，自定义技能映射为 custom-skills，`.system` 不上云。

2. 活跃 AGENTS/CLAUDE、凭据、会话和数据库不进这条支路；原始私有配置由独立的卷影恢复层保存。

3. 安全投影有界：单文件 ≤5 MiB、总量 ≤25 MiB、Python 3.11+；10/3 起新增准入两个布尔键 `memories.token_budget.enabled`、`memories.token_budget.use_history_notes_extension`；其他未知键只记路径、不输出值。

4. 原台式机白名单（AGENTS.md、config.toml、version.json、memories/**、skills/** 等）是已停用的旧选择，仅作退役说明。

5. Git 分支状态和新读远端引用一致是云端完成条件，不抹掉独立的本机和 USB 结果。

## 当前怎样实现

- 笔记本快照存在本机 CodexRecovery 运行根，冷副本在加密 USB 的 `Codex-Recovery\secondary-laptop\codex-data\safe-settings`；对话另有 conversations 目录。缺 USB 不伪造新冷备时间。

- 9/26 起，本机快照之后的复制、长度和哈希都取自这份已捕获的快照，不在等网络时重读活源（防止前后不一致）。

- 笔记本保留 2 份安全快照，网络重试 2/5 秒；不启用“保留较大旧记忆”规则，精确保存本轮输出及删除，Git 自身历史仍在。

## 技术实现与依据（二）

- 台式机旧行为（本机/G 30 份、重试 30/120/300/900 秒、较小 raw_memories 不覆盖、backup-only 不删）代码仍在，只解释留档；不是当前推荐。

- 恢复：当前 README 没有 Restore 章节；恢复边界见 `tools/AGENTS.md` 的相对路径与排除说明和 PCConfig 副机恢复入口。小快照没有专用自动还原器，手工覆盖前先核对目标，排除 .git、tools、日志、快照和本库说明。

## 执行流程

1. 笔记本用显式配置档核对主机、用户、Codex 根和 `backup/<profile_id>` 支路，按白名单选文件并做安全投影。

2. 写本机安全快照并核对，再写加密 USB 冷副本。

3. 从已捕获的快照更新专用云支路；并发暂存的内容会让本次停止。

4. 落后、分叉或网络失败时停止云动作，保留已核对的本机快照；只有新读远端匹配 HEAD 才写完整成功回执。

5. 有实质变更才提交；已有本地超前提交也推送，ls-remote 必须与 HEAD 一致。

## 出问题时

解决什么

避免把数据库和缓存塞进 Git、把私有配置原样上云，也避免把已停的台式机任务和在用的笔记本支路混成一件事，或在一条链失败时误报全部完成。

## 边界

- 9 月 8 日台式机 243 个文件、2.53 MiB，以及 9 月 12 日笔记本安全层 31 个文件、266,762 字节，都是当时的清单，不是容量上限，也不是当前文件数。

- 安全投影按扩展名和秘密特征有界拦截，不是假定任何正文都安全。

- auth.json 与原始会话不在白名单；文件名过滤不等于检查了所有正文里的秘密。

- Codex 的记忆生成与取用开关当前都关着（16:37 观察），这条路线不会持续新增自动记忆。

## 失败与恢复

| 情况 | 怎么办 |
| --- | --- |
| 本地分支落后或与远端分叉 | 报错并拒绝提交和推送，保留已核对的本机快照。 |
| 远端推送后新读引用与 HEAD 不符 | 不写云端完成回执，本机和 USB 结果照旧有效。 |
| 没插加密 USB | 冷副本这层不更新，不伪造新时间。 |
| 要找台式机 9 月 28 日以前的版本 | 去本机/G/H/私有 Git 留档找；G/H 现指向 9/28 11:05:03 那份，151 个文件、1,140,461 字节（16:35 只读元数据，未逐文件重验）。 |
