〔回到项目 → 工作支持与交付〕　〔复制 AI 续作说明〕

工作支持与交付 · 功能说明

一份立项说明或执行计划换版后，只重看真正受到影响的结论。旧结论引用的原话在新版里只出现一次，而且还在原来那一项、那一列或那段上下文里，才把它接到新位置；原话消失、出现多处，或者被挪到了别的事项下，就标明要重新判断，不替我猜。

**当前情况：**资料换版后能保留仍然站得住的结论，标出失效事实和不能再用的旧版文件；“还在原事项里”这条检查是 9 月 24 日补上的。影响范围目前到整次构建，尚不能精确到每份文件或段落；还没有拿真实工作资料的换版验收过。

## 这项功能怎样使用

用途与实际影响

## 为什么需要它

把所有事实一起过期会制造重复劳动；但只看原话还找不找得到也不够：两项工作的日期在新版里互相对调后，每个日期仍然只出现一次，却已经属于另一件事。只重新生成文件却不标旧结果，又会让失效证据继续被引用。

## 举个实际例子

我可以说：“执行计划换成新版了，告诉我哪些结论还能用、哪些文件要重做。”整行换了位置、前面多了一段说明，原话仍在同一事项下的，会自动接到新版；原话被删、出现两次，或者两个系统的上线日期互相对调了，相关事实交回给我重新判断，用到它们的旧版文件标为过期。

## 最后我会得到什么

得到这次换版的处理记录：哪些结论接到了新版、哪些失效待审、哪些旧版交付物不能再当当前版使用。它不是逐字对比的差异文件。处理新增问题后另存新版本；目前影响范围能指出整次构建，尚不能精确到某一页或表格单元。

## 结果怎么看

## 可以正式构建

新资料读得完整，旧结论引用的原话在新版中仍只出现一次、并且还在原来的事项或列下，就自动接到新位置；真正失去依据的结论标为过期。用到变化事实的旧交付版本都不再算当前版，包括刚刚自动接上的事实：结论还能用，但它的证据已经换到新版位置，旧文件要重新生成。

## 需要确认

原话消失、出现多处、被挪到别的事项或列，或新旧说法冲突时，保留两版资料和待确认结论，只让负责人处理对应事实。这时直接“确认”旧证据也会被拒绝，要从新版里补上可靠的原话。

## 当前不可用

新版资料不能可靠读取或保存更新失败时，继续保留上一可靠版本，不假装已经完成换版。

## 从哪里开始

说某份需求或纪要换版了，请核对以前结论哪些受影响。

## 需要准备什么

- 哪份资料发生变化

- 新文件或已保存的新版本

## 从开始到拿到结果

1. **先比较新旧资料**　AI 核对选定来源的新旧内容，完全没变就保持现状。

2. **只重看失去依据的结论**　原话仍只出现一次且还在原事项下的自动接续；消失、重复或换了事项的标待审，并指出受影响的旧交付版本。

3. **确认下一版的范围**　交回仍有效、待审和已过期的部分；待审结论要用新版里可靠的原话重新登记或补证据后才进入新构建。换版本身不会自动生成下一版，旧目录保持可查。

## 技术实现与依据（一）

这里保留实现、关键条件、精确入口、历史记录和验证结果。

精确 rebound（重新绑定）、结构锚点检查、stale fact、stale build 与未关联事实隔离已实现（结构锚点于 2026-09-24 提交 c621e2f 加入，版本仍 0.2.0）；影响仍只到事实和整个 build，未到单文件/单块

## 关键规则与设计选择

1. 相同字节更新是 no-op，不制造 change set 或 stale。

2. 自动 rebound 要同时满足两条：旧 EvidenceSpan 的原文在新版本中唯一存在，并且结构锚点一致（同一事项的位置标记）。CSV 认首列唯一非空的行键和唯一列头；文本认 Markdown 标题层级、所在行或段落的上下文，或完整的“键：值”事项。

3. 任一证据片段原文消失、出现多个匹配，或仍然唯一但已挪到别的事项/列，事实都 stale，不半猜半接。

4. 显式 confirm 旧证据同样检查结构锚点，失配就拒绝；只能登记新事实或补当前可靠证据，人工确认不能绕过失配。

5. 过期 build 的范围是“过期事实 ∪ 重绑事实”：重绑的事实本身保持 fresh，但引用它的旧 current（当前状态） build 仍标 stale。没被该 build 使用、也不改变其正式语义的变化不废旧 build，它仍按自己的修订号 verify；新 build 生成后旧 current 才转 stale。

6. 未关联事实保持 fresh，不要求重复确认；当前 impact 只报告 facts 与 whole builds，没有文件、block、页面或工作表级影响。

7. 下一版仍需处理新增冲突并通过同一 quality gate；来源更新不自动生成下一版。

## 本模块用到的名词

| 名词 | 意思 |

## 出问题时

解决什么

解决一改全废、旧证据继续冒充当前、日期对调后被错接到别的事项、无关事实被误改和重新生成冒充影响分析的问题。

## 边界

- 只做精确原文加结构锚点匹配，不做语义相似重绑

- 多处匹配或事项上下文不足时不猜

- 影响不精确到单Office文件

- 旧build不自动删除

- 来源更新不自动生成下一版

## 失败与恢复

- **新来源与旧版本字节相同**：返回 no-op，不创建人工变化或过期记录。

- **旧原文在新版本出现多次，或仍唯一但已移到别的事项/列**：事实保持 stale，显式确认旧证据也被拒绝；要求登记新事实或补当前可靠证据，不按第一个匹配猜测。

- **更新事务中断**：SQLite 回滚，current（当前状态） snapshot、facts 和 builds 保持上一可靠状态。

## 真实入口

- `PRIVATE source · store.py update_source`快照更新、精确匹配、结构锚点、rebound、stale和事务

- `PRIVATE source · acceptance.py`两套合成来源变化与未关联事实回归（合成验收为 2026-09-01，之后未重跑）

- `PRIVATE tests · core change tests`真实失效、唯一重绑、结构换版案例、无关事实隔离和旧build过期

## 如何验证

- 真实失效事实和引用它们的旧 build 同时 stale；重绑事实保持有效，但引用它的旧 build 仍过期。

- 测试里有 14 种结构换版案例：5 种允许自动接续（如整行挪动、前面插入一段说明），9 种必须过期或拒绝确认旧证据（如两个系统的日期对调、原事项换了列、行键重复、跨标题或同标题下不同事项对调、没有事项的裸日期）。这是 2026-10-11 读源码得到的案例数，本轮没有重跑。

- 未关联事实不被误改；语义不受影响的旧 current build 仍可按原修订号 verify。

- 显式重新确认会再查结构锚点，失配时拒绝。

- 事实/整 build 之外的影响粒度仍未实现；真实工作资料的换版尚未验收。
