# 转换器与 PDF 交付

〔回到项目 → Typora 薄荷主题〕　〔GitHub〕　〔复制 AI 续作说明〕

Typora Theme Pack · 功能说明

把模式和正文交给明确选好的外部转换器，检查这次是否真的成功。现在除了命令行，Typora 的“原版 / 公司 / 个人”三项导出菜单也走这条管道。

**当前情况：**失败保留旧文件、坏 PDF 拒收这些保护在源码里，9 月 29 日 GitHub 自动测试 21 项通过；三项菜单已经配好，但还没在 Typora 里实际点过。新的导出仍核对实际文件，不能借旧 PDF 报成功。

项目源码：公开仓库

## 为什么需要它

有些转换器没有生成文件却返回成功；只检查目标是否存在，就可能把上一次 PDF 冒充本次成果。

## 举个实际例子

原来已有一份 PDF，这次转换器报错。脚本只清本次暂存文件，旧 PDF 保留，并返回真实错误。

## 最后我会得到什么

获得本次生成且可解析的 PDF，或者具体失败原因；不靠旧文件大小判成功。

## 结果怎么看

## 正常时

新 PDF 真实生成、能打开且有页面，原文没有被改动后，才替换目标文件。

## 发现问题时

转换失败或新文件无效时保留旧 PDF，并报告这次没有交付。

## 入口不可用或证据不足时

转换器、输入文件或输出位置不可用时，在替换前停止。

## 从哪里开始

先运行 `python tools/configure_converter.py --converter <converter.py>` 记录兼容转换器，或本次在 export_pdf.py 指定 --converter；再选 Markdown、模式与输出。想从 Typora 菜单导出，运行一次 `configure_typora_menu.py` 写好三项菜单，之后在“文件 → 导出”里选。

## 需要准备什么

- 要导出的 Markdown

- 选定的版式与 PDF 目标

- 如尚未配置，指定已有兼容转换器

## 从开始到拿到结果

1. **准备输入与转换器**　核对原文、输出位置和转换器可运行。

2. **先生成暂存结果**　工具调用转换器后检查原文摘要未变、PDF 可解析且有页。

3. **确认再替换**　仅合格暂存结果替换目标文件；失败留下原文和旧交付物并说明原因。

## 关键规则与设计选择

1. --converter > MD_PDF_TOOLKIT_CONVERTER > 本机 JSON；不猜默认打印器，三处都没有就直接报错。

2. 输出必须为 .pdf，不能等于源 Markdown 或转换器；输入须存在且为 .md，输出父目录必须存在。

3. 暂存文件名短且位于目标同目录，避免跨卷原子移动和长文件名问题。

## 当前怎样实现

- configure_converter.py 原子保存 typora-theme-pack.local.v1；相对路径按配置目录解析。本机配置指向一个已存在的 Markdown 转 PDF 转换脚本，配置里不含任何凭据。

- configure_typora_menu.py 只更新 Typora 的三个自定义导出槽，先备份原配置再原子替换，菜单名为原版/公司/个人；三项都调用 typora_export_launcher.ps1，启动器每次从 PCConfig 登记读取 Python，再把输入和模式交给导出脚本。不传固定输出路径，默认存在文稿旁并带对应后缀。

- export_pdf.py 生成 profile CSS 临时文件，调用 sys.executable + converter，带 --input、--output、--css-file、--document-style-policy、--require-style 和可选 --expected-pages。精确页数由兼容转换器验证；主题包自己的底线是至少一页。

## 边界

- 包不实现底层 PDF 排版；兼容引擎由用户既有配置提供。

## 失败与恢复

- **无输出、损坏 PDF、0 页或非零退出**：保留旧目标并报告失败。

- **源摘要变化**：拒绝交付，不把变动文件对应的 PDF 写成已验证。
